2. Mechanism of the fix
================================================================================

(1) Pins (7a2ea963). Every action is `owner/repo@<40-hex>  # vX.Y.Z`
(checkout v4.4.0 11d5960a, setup-buildx v3.12.0 8d2750c6, build-push v6.19.2
10e90e36, cache v4.3.0 0057852b, upload-artifact v4.6.2 ea165f8d, setup-go
v5.6.0 40f1582b, each resolved with `git ls-remote` against its major tag on
2026-09-24); setup-buildx runs moby/buildkit:buildx-stable-1@sha256:28a89871.
The two project-image FROMs carry "# pins-check: project-image". The inline
image:tag@sha256 form was kept (the brief's "tag as a comment"): Docker
resolves the digest and ignores the tag, and the tag stays readable.
scripts/pins-check.sh (bash 3.2+, git, grep/awk; no container) fails on any
movable FROM/uses/image/driver image, and the new `pins` job in tests.yml
runs its --self-test and then the check.

(2) Inputs lock (85e453e2). tools/build-inputs/inputs.lock: 41 lines
NAME ARCH SCOPE SHA256 PURL. tools/build-inputs/verify-inputs.sh runs inside
both builds, after each download and BEFORE anything loads, executes or
compiles it:
  - git c-kzg-4844 / blst: HEAD must be 28743bc8 (v2.1.1) / 8c7db7fe
    (v0.3.14), and a content tree digest (sha256 over the sorted sha256sum
    listing, .git excluded) must match -- identical on arm64 and amd64;
  - deb sbcl: installed version 2:2.2.9-1 (also pinned in the runtime apt
    line), plus a per-arch digest of its /usr/bin and /usr/lib/sbcl files
    (amd64 47fdeb7f.., arm64 93fbb6fc..);
  - Quicklisp: client 2021-02-13, setup.lisp, asdf.lisp over HTTPS, checked
    against their client-info.sexp sha256 BEFORE SBCL loads them; laid out
    as quickstart would, with dists/ pre-created so the moving default dist
    is never installed; then install-dist 2026-01-01 and only a DOWNLOAD of
    the releases QUICKLOAD would load (ql::compute-load-strategy +
    ql-dist:ensure-installed); then distinfo/systems/releases and every
    archives/*.tgz checked (an archive without a line fails, and so does an
    empty archives/). 8 archives in the runtime image, 30 in the test image.
  - the steps that compile afterwards run `RUN --network=none` (the test
    image's QUICKLOAD of ironclad, cffi, mgl-pax/full; the runtime image's
    SAVE-LISP-AND-DIE), so nothing unverified can be fetched late.
The quicklisp.lisp bootstrap is gone. The lock is COPYed after the RocksDB
layer, so a lock change never recompiles RocksDB; scripts/dev.sh folds the
lock and verifier into the dev/cold image fingerprint; .dockerignore admits
them. pins-check.sh also checks the lock from the control plane: well-formed
lines, every digest recorded (no TBD), no duplicate, every name a Dockerfile
verifies is listed, and the vendored RocksDB tarball and both inline RocksDB
digests equal the lock.

(3) SBOM (ed61958d). scripts/release-artifacts.sh sbom, called by
runtime-export, writes ARTIFACT.sbom.cdx.json (CycloneDX 1.5) with no SBOM
tool: the image itself is run (no network, read-only, no capabilities, its
own non-root user) to list dpkg packages and sha256 every file under
/usr/local and /opt; build inputs come from inputs.lock AT THE IMAGE'S
REVISION (git show), marked "required" (in the image) or "excluded"
(build-only). Deterministic: commit-time timestamp, serial derived from the
image ID. validate-sbom runs the CycloneDX project's validator
(cyclonedx/cyclonedx-cli:0.33.1 by index digest, no network).

(4) Provenance, signing, verification (38b1abbe, 709616fc). runtime-export
also writes ARTIFACT.provenance.json (in-toto Statement v1, SLSA provenance
v1: subject = archive name + sha256; source repo + commit; inputs.lock
sha256; base image as pkg:docker/debian@sha256:..?tag=bookworm-slim;
builder = scripts/dev.sh runtime-build at that commit + Docker server
version; invocationId = image ID; SBOM sha256 as byproduct) and
ARTIFACT.SHA256SUMS over the three. `scripts/dev.sh runtime-sign ARTIFACT`
signs SHA256SUMS with cosign v2.6.5 (gcr.io/projectsigstore/cosign by index
digest; no network, read-only, no capabilities, host uid) and the key file
COSIGN_KEY, unlocked by COSIGN_PASSWORD from the environment; a key inside
the checkout is refused; no transparency-log upload. generate-key makes an
encrypted pair outside the checkout. scripts/release-verify.sh ARTIFACT
PUBKEY checks offline, in order: signature; SHA256SUMS names exactly the
three files and each matches; every archive blob hashes to its name, the
SBOM's image ID is the archive's index entry and reaches the config that
manifest.json names, whose revision label is the recorded revision;
provenance subject/commit/lock/invocation/SBOM byproduct agree; SBOM valid
CycloneDX 1.5; inputs.lock at that commit hashes to the recorded digest when
the checkout has the commit. No JSON tool on the host (the documents are read
in the exact layout the generator writes; anything else fails).

================================================================================
Not verified
================================================================================

- Reproducibility. Two builds of the same revision were not compared bit for
  bit, and the SBCL executable (SAVE-LISP-AND-DIE) is not known to be
  reproducible. Only the SBOM is shown deterministic.
- The runtime stage's Debian libraries (libsecp256k1-1, libstdc++6, ...) are
  installed by name from bookworm, not pinned: the SBOM lists their exact
  versions, the lock does not hold them, and apt's own signature checks are
  the only authentication. Same for the builder stages' toolchains
  (build-essential, git) and the golang base's apt layer in the test image.
- The test image's first apt layer still installs `sbcl` unversioned (pinning
  it there would rebuild RocksDB for every developer); the later
  verify-inputs.sh deb check fails that build closed if the version or files
  drift.
- The Quicklisp client and dist fetch the dist indexes and archives over
  HTTP; integrity rests on the lock digests checked before use, not on the
  transport.
- Keyless (OIDC/Fulcio/Rekor) signing is not implemented; only the key-file
  path is, and no real release key exists yet. The provenance is
  self-attested (SLSA Build L1), not from a hosted builder.
- setup-go resolves go-version '1.24' to the newest 1.24.x at run time, and
  setup-buildx uses the runner's buildx binary: both remain runner-side
  inputs outside the pins.
- The CI `pins` job has not run on GitHub.
