1. SIGKILL recovery (tests/ops-recovery-tests.lisp, layer e2e)

Shape. scripts/ops-crash-worker.lisp MODE WORKDIR loads the test system and
runs one production operation on a RocksDB store under WORKDIR, publishing
progress to WORKDIR/marker.sexp (temp file + rename). The parent waits for a
marker predicate, sends SIGKILL (uiop:terminate-process :urgent t; status 137
every time), reopens the store in-process, records what it holds, resumes the
operation, and compares with a control run of the same operation into a
separate RocksDB directory that nobody interrupted. Build and reorg run the
shipped CLI (ETHEREUM-LISP.CLI:MAIN, --db.engine rocksdb, Engine port with JWT)
and the parent drives it over HTTP; the child only adds a hook that announces
itself and holds the step open.

RED control of every test: the kill landed mid-operation -- the marker counted
work, never reports completion or release, and the reopened store holds
strictly less than the finished operation writes. Observed values (cold e2e):

  (a) SNAP range phase with a storage plan
      fixture: 403 accounts, three with 40-slot storage tries capped by a
      350-byte StorageRanges limit (48 account pages in all)
      kill at     pages 12, deferred-storage works 3
      reopened    progress present, completed NIL, 3 deferred works durable
      resumed     completed T, installed root = source root,
                  742 of 742 source trie nodes present byte-for-byte
      control     completed T, 742 of 742

  (b) healer mid-walk
      fixture: 4,096 accounts, range phase complete, healer from the durable
      progress with 64 KiB responses (15 GetTrieNodes round trips)
      kill at     6 responses, root durable (first 100 KiB flush landed)
      reopened    completed NIL, 705 of 5,589 nodes present, 705 marked
      resumed     completed T, 5,589 of 5,589, 0 marked, fetched 4,884
                  (= 5,589 - 705: resumed, did not restart)

  (c) forward batch importer mid-batch
      fixture: 24 empty blocks, one peer response, 150 ms per block, 1 s
      guard-hold budget

                  durable cursor resume-start 9 with block 8 as parent,
                  head 0 (forward import never publishes forkchoice)

  (d) payload build (real node)

                  (0xcf2263fb...), equal to the control's summary

2. SIGTERM deadlines for build and reorg (layer e2e)

The same real-node workers with the hook holding for 8 s -- longer than the
5 s in-flight drain (*ENGINE-RPC-HTTP-SHUTDOWN-DRAIN-SECONDS*), so the
connection is abandoned and the shutdown export waits for the store guard.
RED control: the marker at the signal is the held phase, not released.

  build   SIGTERM -> exit 0 in 8.01 s (cold), 8.05 s (warm); RocksDB LOG
          "Shutdown complete" x1; the build finished during the stop
  reorg   SIGTERM -> exit 0 in 8.05 s (cold), 8.03 s (warm); LOG close x1;
          reopened head B3, chain whole: the stop waited for the rewrite
          instead of cutting it

Finding (not fixed, recorded in docs/runbook.md "Stop"): the stop lasts as
long as the longest guard-holding request in flight, bounded only by that
request's 30 s deadline. Probe with the hold raised to 30 s
(ETHEREUM_LISP_OPS_HOLD_SECONDS=30, warm image, not a committed test):

  stop-to-exit 30.03 s / 30.04 s, exit 0, LOG close x1; the worker log shows
  engine.rpc.http.listener.abandoned then engine.rpc.http.connection.error
  "HTTP request exceeded the 30 second deadline" -- the deadline, not the
  stop, released the guard.

Under `docker stop --time 30` that is a SIGKILL (exit 137). The committed
test asserts the 20 s budget at 8 s and goes red at 30 s. Closing it means
interrupting an in-flight Engine handler at shutdown, which is Engine-guard /
shutdown code outside this brief.

3. Metrics (a560644b)

Plan list (Section 10) against the endpoint before this branch: event counts,
txpool levels, head/safe/finalized number, peer count. Added, each a lock-free
read so a scrape never waits for the store guard:

  ethereum_lisp_sync_head_number / _sync_target_number / _sync_lag_blocks
      from the sync view published at every guard release plus the durable
      SNAP skeleton target
  ethereum_lisp_snap_pivot_number / _snap_state_complete
      RocksDB point read of the SNAP progress
  ethereum_lisp_peers_inbound / _outbound / _eth / _snap
      under the peer-table mutex (not the store guard)
  ethereum_lisp_database_bytes            file sizes under the database path
  ethereum_lisp_process_resident_bytes    /proc/self/status VmRSS
  ethereum_lisp_heap_used_bytes / _heap_allocated_bytes_total / _gc_ms_total
  ethereum_lisp_<family>_{last_ms,max_ms,ms_total,requests_total} for
      engine_new_payload, engine_forkchoice_updated, engine_get_payload,
      engine_other, rpc, rpc_batch -- handlerMs of every
      engine.rpc.http.request event, recorded by a sink layered under the
      counting sink
  A gauge named *_total is declared a counter in the exposition.

reorg depth/count, pruning progress, RocksDB internal errors and cache or
compaction pressure, peer quality scores.
