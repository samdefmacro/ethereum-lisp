Section 5: EVM interpreter throughput on Hoodi gas-burner blocks

Status

Branch evm-throughput, from 886afd05. DONE LOCALLY: a full Hoodi-shaped
gas-burner block (24 x 2.49M gas) imported through engine_newPayloadV2 now
costs 181-217 ms of CPU and 3-5 MB consed on the arm64 dev image, against

Not deployed; no live run; no cold-all (the coordinator runs it once). No

================================================================================
1. What the time was
================================================================================

The Hoodi burner (0x6b3f1c2aa4f0a2a49bb782a4e83db5a0764326ec, code
0x5f5a5f600e565b5f5260205fa1005b6127105a1060065760010161133750600e56; see
docs/evidence/sec5-newpayload-six-second-cpu.txt) is a 12-instruction,
44-gas loop: JUMPDEST PUSH2 GAS LT PUSH1 JUMPI PUSH1 ADD PUSH2 POP PUSH1 JUMP,
about 680,000 instructions per transaction. At 886afd05 every instruction
paid for, in order of cost:

  - generic arithmetic on PC, STEPS, GAS-USED and the gas budget (slots typed
    (integer 0 *), so every INCF / compare was a full call to
    SB-KERNEL:TWO-ARG-+ / TWO-ARG-< ...; 16-20% of samples);
  - the list stack: one cons (16 bytes) per push, the REST value threaded
    through every handler, a special-variable depth cell touched on every
    push and pop (8.9 MB per frame, all of the frame's garbage);
  - one closure per comparison (EVM-MACHINE-APPLY-COMPARISON built a lambda
    over its predicate per LT/GT/EQ);
  - PUSH immediates and JUMP targets read with generic arithmetic on an
    untyped code vector.

sb-sprof (:cpu, inside a spawned thread; see "Not verified" for the
profiler's own trouble) after the vector stack (94a0ade3):
  TWO-ARG-+ 20%, STEP-EVM-MACHINE 15%, EXECUTE-OPCODE 10%,
  EXECUTE-STATE-MEMORY-OPCODE 10%, EVM-MACHINE-CHARGE-GAS 8%,
  READ-PUSH-IMMEDIATE 7%, EVM-GAS-BUDGET-CHARGE-REGULAR 6%, TWO-ARG-< 5%
and after the fixnum gas/PC charge (0db8897f):
  STEP-EVM-MACHINE 27% (the inlined charge), TWO-ARG-< 14% (untyped word
  comparisons and the frame loop), TWO-ARG-+ 9% (PUSH immediates, ADD),
  READ-PUSH-IMMEDIATE 7%, LENGTH 6%.

================================================================================
2. Changes
================================================================================

94a0ade3 (src/runtime/evm/interpreter/machine.lisp, opcodes/*.lisp,
interpreter/call.lisp, base.lisp, execute.lisp, types.lisp): the machine owns
a simple-vector stack that starts at 16 slots and doubles up to
+STACK-LIMIT+ (1024), and an SP slot typed (integer 0 1024). Handlers pop and
push through EVM-STACK-POP / EVM-STACK-PUSH / EVM-STACK-PUSH-WORD in the same
order the list code popped, so underflow, overflow (sp >= 1024 before a push)
and out-of-gas are raised at the same points with the same messages;
DUP/SWAP/DUPN/SWAPN/EXCHANGE index the vector at the same depths. A failed
frame is discarded (EVM-MACHINE-RESULT is only built on a normal halt), so
the earlier in-place pop before a failing charge is unobservable.
EVM-RESULT-STACK keeps its list shape, top first (EVM-STACK-LIST). POP1..POP7,
STACK-PUSH, *EVM-STACK-DEPTH-CELL*, the CALL message's REST-STACK slot and the
comparison closure are gone.

0db8897f: PC and STEPS are (and fixnum unsigned-byte) (PC only ever holds a
code offset; a jump target is checked against the code length before it is
stored). The per-instruction base-gas charge goes through an inline
%EVM-MACHINE-CHARGE-GAS that runs on fixnum arithmetic when the amount, the
budget's REGULAR and USED-REGULAR and the frame's GAS-USED are all fixnums,
and otherwise calls the unchanged general EVM-MACHINE-CHARGE-GAS. The
unaffordable case fails with the same "EVM out of gas (regular dimension) at
pc N" before any counter moves, as EVM-GAS-BUDGET-CHARGE-REGULAR did. Gas
limits above 2^62 (EEST uses some) take the general path.

3e56d398: ADD SUB AND OR XOR LT GT EQ evaluate the operator under a fixnum
type test first and generically otherwise (EVM-WORD-BINARY /
EVM-WORD-COMPARISON); both branches compute the same value and the push
still reduces modulo 2^256. PUSH1..PUSH7 immediates are read with word
arithmetic from the typed code vector; a fixnum JUMP target is checked
against the typed code and the JUMPDEST bitmap without generic compares (a
larger target is past any code, as before); STEP-EVM-MACHINE is inlined into
the frame loop over the typed code length.

e8f58512 (memory.lisp, opcodes.lisp, base.lisp): MSTORE and MLOAD work on
the displaced view's simple backing vector, with a fixnum path (no bignum)
and otherwise eight 32-bit pieces instead of a shifted integer per byte;
PUSH8..PUSH32 immediates are assembled from 32-bit pieces; WORD returns a
bignum already below 2^256 instead of dividing it. The burner barely uses
memory, so this is for ordinary contract code: a 2.47M-gas loop that stores
and reloads 0xabab..ab (PUSH32, MSTORE, MLOAD per iteration) went from
155-177 ms / 320 MB to 54-73 ms / 82 MB (200-222 ms / 329 MB at 886afd05).

What was not changed: the memory representation itself (still a displaced
view over a doubling backing vector), 256-bit arithmetic above 2^62 (still
Lisp bignums), the family dispatch (a range COND into five handler
functions), the step budget and the gas budget structure.
