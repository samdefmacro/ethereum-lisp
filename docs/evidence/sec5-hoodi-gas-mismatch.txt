  Then 113 descendants answered INVALID "links to previously rejected block",
  and the upgraded 04a3aff4 on the same datadir refused the block again

It is NOT a gas rule and NOT the fork schedule. Our EVM charges exactly what
go-ethereum charges for all eleven transactions. The defect is a storage READ
on the lazily-backed state the node executes on: a slot first read after its
account's journal entry lost its value when a call frame reverted, and read
as zero for the rest of the state's life. Transaction 9 of the block
(0xff0ed042a61bbb2000141154f326a90488a4d19c30e7d91e15592300a143025d, six
reverted frames) then took another path and used 323,810 gas instead of
geth's 342,412: 18,602 less, the whole difference. A second defect made the
verdict permanent: INVALID verdicts were persisted and restored at startup,
so the fixed binary could never re-execute the block. go-ethereum keeps its
verdicts in memory only. Not deployed; no live run; no cold-all (the
coordinator runs it once at the end).

================================================================================
2. Mechanism
================================================================================

The node executes on MAKE-LAZY-STATE-DB (src/application/services/
execution.lisp CHAIN-STORE-STATE-DB): accounts come from a loader, storage
from each account's persisted storage trie, and each account's STORAGE hash
table is only a cache of the slots read so far. Which slots had been read
was recorded in ONE state-wide table, LOADED-STORAGE, as "address:slot".

A journal entry (STATE-DB-RECORD-CHANGE) stores a clone of the account
object, storage cache included, at its first write. When a call frame
reverts, STATE-DB-REVERT-TO-SNAPSHOT puts that clone back. A slot FIRST READ
after the clone was taken is in the reverted object's cache but not in the
clone, while LOADED-STORAGE, which no revert touches, still says it was
read. STATE-DB-GET-STORAGE therefore skipped the backing and answered
(gethash slot storage 0): zero, for as long as the state object lived (the
node keeps it across blocks).

go-ethereum separates the two on purpose (core/state/state_object.go):
originStorage caches committed values and is never journaled;
dirtyStorage/pendingStorage hold writes and are reverted
(core/state/journal.go storageChange.revert).

Minimal shape (test BACKED-STATE-READ-IN-A-REVERTED-FRAME-SURVIVES-THE-
REVERT): a contract CALLs itself; the inner frame writes slot 1 (journals the
account), reads slot 2 = 42 for the first time, and REVERTs; the outer frame
copies slot 2 to slot 3. At 04a3aff4:

  state                      status  gas     slot 3
  in-memory (EEST's state)   1       69,578  42
  lazy, flat storage loader  1       49,678  0
  lazy, storage trie (node)  1       49,678  0

The in-memory state never shows it: all of its storage sits in the table
from the start, so every clone has every slot. That is why EEST v20.0.2
passed 8/8 on the same revision.

================================================================================
4. Fix
================================================================================

72d148aa (src/runtime/state/types.lisp, db.lisp). What an account object
knows about its slots now lives on the object and travels with its clone:

  STATE-OBJECT BACKED-P   true only for an object the account loader made;
                          its STORAGE is a partial cache of a backing
  STATE-OBJECT ZERO-SLOTS slots of a backed object known to hold zero (read
                          as zero, or deleted here)

STATE-DB-GET-STORAGE: in STORAGE -> that value; not backed -> 0; in
ZERO-SLOTS -> 0; else read the backing (the object's storage trie, else the
flat loader) and remember it on the object. CLONE-STATE-OBJECT copies both.
The state-wide LOADED-STORAGE table is gone. A revert that restores a clone
now restores exactly what that clone knew; a slot first read after it is
read from the backing again, which is correct because every write reads its
slot first (STATE-DB-SET-STORAGE preserves the before-image), so a slot
first read after the clone was unwritten when the clone was taken. A slot
deleted before a snapshot stays deleted (ZERO-SLOTS is in the clone). Clones
copy one more (usually empty) table; the per-slot "address:slot" FORMAT
string on every storage read is gone.

60fb6e91 (src/storage/node-store/persistence/import/side-data.lisp,
orchestrator.lisp, src/app/cli/devnet/persistence.lisp). A verdict belongs
to the process that reached it:

  - direct (RocksDB) startup, DEVNET-CLI-IMPORT-DIRECT-CHAIN-DATABASE, calls
    the new NODE-STORE-DISCARD-INVALID-TIPSETS-FROM-KV instead of
    NODE-STORE-IMPORT-BOUNDED-INVALID-TIPSETS-FROM-KV: every persisted
    :invalid-tipset record is deleted in the existing bounded,
    BAL-owner-atomic pages (NODE-STORE-CLEAN-BOUNDED-INVALID-RECOVERY-
    RECORDS), before any request is served;
  - the hydrating startup (DEVNET-CLI-IMPORT-CHAIN-DATABASE) passes the new
    NODE-STORE-IMPORT-FROM-KV :IMPORT-INVALID-TIPSETS-P NIL.

Within a process nothing changed: ENGINE-PAYLOAD-STORE-MARK-INVALID, the
invalid-ancestor walk, the 128-hit eviction and the export of verdicts are
as before (the Hive "invalid ancestor" semantics are within one process).
Reference: go-ethereum v1.17 (checked in the v1.17.6 reference tree)
eth/catalyst/api.go invalidBlocksHits / invalidTipsets, "Ephemeral cache",
invalidBlockHitEviction = 128, invalidTipsetsCap = 512; core/blockchain.go
reportBadBlock -> rawdb.WriteBadBlock (core/rawdb/accessors_chain.go,
badBlockToKeep = 10) is read only by debug_getBadBlocks and the tracers
(eth/api_debug.go, eth/tracers/api.go), never on import.

Not changed: the staged-import hydration (staged-import.lisp) still imports
verdicts; it runs inside a live process, not at startup.

runtime built from this branch (both fixes) on the same datadir: direct
startup deletes every persisted verdict, 0x8da352f3 included, before the
