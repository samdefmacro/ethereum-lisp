Forensics on the preserved datadir (copied; RocksDB opens read-write): a scan
of every :trie-node record, 359,878,472 of them, found NO record that
references 0x7cf22bf1...; the hash carries no marker and no proof. So no
present node stands above it and the healed state has no hole. The hash is
a storage root that existed only in memory: the forward peer-sync batch
importer (devnet-peer-sync-import-batch) executes several blocks of one
response before exporting, and a block two or more positions after the one
that changed a contract's storage looked that storage trie up on disk, where
its new root had never been written (chain-store-state-db and
node-store-direct-storage-trie searched only the parent's pending tries;
the account trie was carried forward, the storage tries were not). The error
escapes the sync coordinator's handled set by design and takes the node down.
Reproduced RED at the unit level and through the real batch importer with
signed contract-writing blocks, fixed at aaeb549c (merge 8e95b990) by
searching every unexported ancestor's pending tries on both paths.

Unexplained and carried forward: the Engine deadline timeouts from 04:27Z,
six minutes before the exit. Possibly the store guard held across batch
retries; not investigated.

What this run establishes

- Under closure epoch seven with the stale storage markers cleared at write
  time and the read width kept wide, a fresh-datadir Hoodi heal converges in
  under a minute per generation, including after pivot rebases.
- The remaining Section 5 work is downstream of healing: the forward batch
  importer's overlay (fixed), the closure walk's cost (fixed, unmeasured
  live), and the Engine timeouts during forward sync (open).
