Scope

This file is about the CONSTANT FACTOR of the healer's local walk, not about
which nodes it walks. Whether the healer should descend into present, unmarked
account subtrees after a pivot rebase is a separate, concurrent piece of work
(docs/snap-account-closure.md, sec5-3305307d-hoodi-stall.txt). Nothing recorded
here changes the skip/descend decision, the closure epoch, or the completion
predicate.

The question is narrower: the 3305307d Hoodi sample walks nodes that are
already present in the local RocksDB store at processedRate 260 nodes/s while
the container burns 111% of eight cores. That is ~4.3 ms of CPU per node for
what should be a point read, an RLP decode and a Keccak check. A 10-100x
constant-factor win shortens every heal regardless of which closure design
lands.

Finding 1: the local read batch collapsed to width 1 once the frontier passed
131,072 works (VERIFIED)

SNAP-SYNC-HEAL-LOCAL-READ-LIMIT (3348 at a324d868) computed

  frontier-limit  = +snap-sync-heal-live-frontier-max-works+ = 131,072
                    (8,192 only while the frontier is at or below the
                     4,096-work checkpoint soft target)
  expansion-room  = floor(max(0, frontier-limit - stack-count) / 63)
  read-limit      = min(4096, missing-room, checkpoint-room, max(1, expansion-room))

With the live frontier at 909,342 the subtraction saturates at 0, so
expansion-room is 0 and read-limit is exactly 1. Every node then becomes its
own read batch: its own healed-subtree presence MultiGet, its own
account-subtree dependency MultiGet, its own trie-node/marker MultiGet. (The
reading above said each also paid a dispatch through the eight-thread read
pool. It does not: a one-reference batch is below
+SNAP-SYNC-HEAL-PARALLEL-READ-MINIMUM+ and takes the serial path, so the three
MultiGets run on the coordinator thread.)

The bound it enforces -- "one batch must not push the frontier past
frontier-limit" -- is already violated at that point and returning 1 does not
restore it. What fills the frontier is blocked post-order sentinels: while any
missing work is pending in the pass, every :NODE-COMPLETE and :COMPLETE
sentinel the walk reaches is moved to BLOCKED-COMPLETIONS and still counted, so
the frontier grows by about one work per marked node visited, whatever the
batch width. That is also why the Hoodi frontier (909,342) is so close to
knownIncompleteNodes (796,382).

The bounded pipeline refill (COLLECT-MISSING with BOUNDED-REFILL-P) has its own
loop guard on the same bound and does no local work above it. That is by
design -- a saturated generation must return to the event loop -- and it is
left exactly as it was.

Fixtures

A. Realistic. 150,000 accounts at Keccak keys, plus two accounts at keys
   00..00 and FF..FF whose leaves are withheld from the store, so the walk
   finds missing work at whichever end of the root it pops first. 208,318
   stored trie nodes, all written through
   SNAP-SYNC-POPULATE-VERIFIED-TRIE-RECORDS-BATCH, every one marked incomplete
   (the Hoodi mode: knownIncompleteNodes / processedNodes = 0.99), in a real
   RocksDB store on the container tmpfs, complete-node scheme enabled. The
   walk runs through the shipped SNAP-SYNC-HEAL-STATE until it asks the one
   source for the two missing leaves; the source then fails and the run ends.
   Counts come from wrapping KV-GET-MANY and
   SNAP-SYNC-HEAL-LOCAL-NODE-AND-INCOMPLETE-BATCH, nodes/s from the healer's
   own progress snapshots every 2,048 processed nodes. The scratch harness is
   not in git.

B. Regression. SNAP-HEAL-WALK-SHARED-SUBTREE-TRIE: a real trie whose three
   depth-one children share one 16-ary subtree, so six stored nodes are walked
   209,716 times; two depth-one leaves are never stored. It is the fixture of
   SNAP-HEAL-LOCAL-WALK-KEEPS-WIDE-READS-ABOVE-THE-LIVE-FRONTIER-BOUND.

The fixes

1. Width (67039a6e). In the live region the read width never falls below
   +SNAP-SYNC-HEAL-LIVE-OVERFLOW-READ-WIDTH+ = floor(8,192 / 63) = 130, so one
   batch overshoots the live bound by at most one durable checkpoint's worth of
   works (8,190). The checkpoint region keeps its exact rule, and the bounded
   pipeline refill passes a width of one, so its behaviour is unchanged. The
   frontier-max-works bound itself is not raised.
2. Per-node CPU (7e9d8cab). Paths and identifiers are built once, directly as
   octet vectors; empty branch children build no path; short nodes decode
   their hex-prefix path straight into the extended path; the three per-node
   node-hash tables keep an EQUALP test with a hash over the first seven
   octets of the Keccak hash.
3. Observability. The heal progress snapshot and peer.snap.heal_progress now
   carry localReadBatches and localReadWorks, whose ratio is the mean local
   read width, so the next live run can confirm the width directly.

A second finding, not changed here: the read pool on small batches

When no missing work is pending, post-order sentinels are not blocked, every
marked node's sentinel splits the batch, and the mean width is 3.6. Fixture A
without the two withheld leaves (208,320 nodes, completes the heal):

  local read workers 8 (production)   21.1 s on the parent; 21.2 - 23.7 s
                                      after both changes, one outlier 80 s;
                                      535,342 MultiGets, 58,319 batches in all
  local read workers 1 (both changes) 3.5 s, 174,409 MultiGets

Handing a two-to-five reference batch to the pool costs ~90-150 us per job on
this VM (micro: node+marker read of two references pooled 87.7 us, serial
6.6 us; sixteen references pooled 172 us, serial 48 us; 128 references pooled
220 us, serial 371 us). In the blocked mode the pool still pays: fixture A
with one worker takes 2.3 s against 1.5-1.9 s with eight. On a disk-backed
store a cold point read costs far more than a memtable hit, and the pool
exists for that case, so +SNAP-SYNC-HEAL-PARALLEL-READ-MINIMUM+ is left alone
until the Hoodi host can A/B *SNAP-SYNC-HEAL-LOCAL-READ-WORKERS*.

Not verified

  worst width-one rate measured here is ~22 us per node on a memtable-resident
  store. Most of the Hoodi per-node cost is therefore somewhere this fixture
  does not reach -- most likely cold RocksDB block reads (read, checksum,
  decompress) on a large store -- and the size of the live gain is not
  predicted by these numbers. The new localReadBatches/localReadWorks fields
  are how the next run shows whether the width actually changed.
