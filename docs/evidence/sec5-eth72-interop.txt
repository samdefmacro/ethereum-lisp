Section 5: eth/72 sessions died on "GetCells must contain exactly 3 items"

Status

Branch eth72-interop, from 1a7b9059 (sec5-public-bootstrap-sync head,
1a7b9059fef8ab705e6b0b56db831c7e6adef911). Cause found, reproduced and fixed
locally. Not deployed, no live run, no Hive run, no cold-all (the
coordinator runs it once at the end).

Deployed geth has two GetCells/Cells packet layouts under the one eth/72
version. Our codec followed the newer one (geth v1.17.6 and the devp2p
text); the Hoodi peers that sent GetCells used the older one (geth v1.17.5).
The decode error ended the whole session, including its snap/1 source.

Revision

  635a9667  eth-wire: read both deployed eth/72 GetCells/Cells layouts and
            answer in the requester's

================================================================================
2. The wire shapes, and why ours disagreed
================================================================================

devp2p caps/eth.md (master, fetched 2026-09-29):
  GetCells (0x14) [request-id: P, [txhash1: B_32, ...], cells: B_16]
  Cells (0x15)    [request-id: P, [txhash1: B_32, ...],
                   [[cell1: B_2048, ...], ...], cells: B_16]
  The eth/66 envelope is the request id as the FIRST ELEMENT of the message
  list, not a [request-id, payload] pair; there are no extra fields.

geth releases (tags from the GitHub API; source fetched 2026-09-29):
  v1.17.4 (36a7dc72)  ProtocolVersions {71, 70, 69}: no eth/72 at all.
  v1.17.5 (9621c6ad)  ProtocolVersions {72, 71, 70, 69}, lengths
                      {69:18, 70:18, 71:20, 72:22}.
                        type GetCellsRequestPacket struct {
                            RequestId uint64
                            GetCellsRequest        // {Hashes, Mask}
                        }
                        type CellsPacket struct {
                            RequestId uint64
                            CellsResponse          // {Hashes, Cells, Mask}
                        }
                      geth's RLP encodes an embedded struct as ONE nested
                      field (as it does for GetBlockHeadersPacket's
                      *GetBlockHeadersRequest), so the wire is
                        GetCells [id, [hashes, mask]]           2 items
                        Cells    [id, [hashes, cells, mask]]    2 items
                      Peer.RequestPayload sends it, Peer.ReplyCells replies
                      with it, handleGetCells/handleCells decode only it.
  38271784 (#35428, 2026-07-28, "eth/protocols: fix Cells/GetCells RLP
                      encoding"): "Previously, GetCellsPacket and CellsPacket
                      embedded GetCellsRequest and CellsResponse. This caused
                      them to be encoded as nested lists, which does not match
                      the wire format defined by the spec." The fields are
                      inlined: [id, hashes, mask] and [id, hashes, cells,
                      mask]. No version bump, no protocol-length change.
  v1.17.6 (3d84c6b2)  contains 38271784: flat. The v1.17.5..v1.17.6 compare
                      shows no other change to eth/protocols/eth wire types
                      (NewPooledTransactionHashesPacket72, BAL packets,
                      Receipts and Status are identical in both).

Why ours disagreed: this repository's pinned reference checkout is
go-ethereum 1.17.6-unstable at exactly 38271784 (docs/reference-map.md), the
flattening commit, so the codec implemented the flat layout. The only
release that advertises eth/72 and predates the fix is v1.17.5, whose
GetCells has two items where we required three; that is the logged error.
A v1.17.5 peer would equally fail to decode our flat Cells reply and our
flat GetCells (its handleCells/handleGetCells return the decode error), so
one layout cannot serve both releases.

geth itself is not interoperable across the two: v1.17.6 handleGetCells
(eth/protocols/eth/handlers.go:691-696 at 38271784) returns the decode
error, eth/protocols/eth/handler.go Handle returns it from the message loop,
and p2p/peer.go run (lines 307-311) disconnects with discReasonForError,
i.e. DiscSubprotocolError. Our session teardown on a decode error is
therefore geth's behaviour; the defect was only which layouts we accept.

================================================================================
3. Fix (635a9667)
================================================================================

src/protocol/eth-wire/messages.lisp
  ETH-CELLS-PACKET-FIELDS splits a decoded GetCells/Cells into its request
  id, its fields and the layout read: 1+N items is :FLAT, 2 items whose
  second is a list of exactly N items is :NESTED; anything else is an error
  naming both expected shapes. DECODE-ETH-GET-CELLS and DECODE-ETH-CELLS
  return the layout as an extra (last) value; ENCODE-ETH-GET-CELLS and
  ENCODE-ETH-CELLS take :DIALECT (:FLAT default, the devp2p text).
src/networking/eth-sync/serve.lisp
  A GetCells is answered with Cells in the request's layout, and the peer's
  layout is remembered.
src/networking/eth-sync/peer.lisp, fetch.lisp
  ETH-PEER-CELLS-DIALECT: the layout the peer last sent (GetCells or Cells),
  else ETH-CELLS-DIALECT-FOR-CLIENT-ID, which answers :NESTED only when the
  Hello client id is Geth[/identity]/v1.17.5[-...]/... (geth
  node.Config.NodeName), else :FLAT. ETH-PEER-GET-CELLS sends in that layout
  and reads the reply in either.

A shape neither geth sends (a trailing extra field, a nested list with a
missing or extra field, a bare request id) remains a session-ending
protocol error, as in geth.

Every embedded slice type (GetBlockBodiesRequest and the like) is one field
holding a list, which our decoders already read as the second item; only the
two embedded STRUCTS matter, and GetBlockHeadersRequest was already nested
on our side. GetCells/Cells were the only envelope mismatch.

The three inbound "eth/69 Status must contain exactly 7 items" failures are
not this mistake: geth's readStatusMsg (eth/protocols/eth/handshake.go:97-
109) decodes the same seven-field StatusPacket strictly and ends the
handshake on any other count. Which client sent them is not logged.
