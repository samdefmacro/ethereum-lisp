Observed failure boundary

The active exact-0c6b51bf Hoodi deployment continued to report authenticated
Engine connection failures of the form:

  HTTP request exceeded the 30 second deadline

A six-hour read-only sample ending 2026-09-13T12:46:50Z contained eleven
`engine.rpc.http.connection.error` events. Both the EL and Lighthouse remained
running with zero restarts and no OOM. This observation identifies the live
boundary but does not validate the successor because 0cffbcb4 is not deployed.

The deterministic pre-fix control selected
`ENGINE-RPC-HTTP-PERSISTENT-IDLE-WAIT-OUTLIVES-REQUEST-DEADLINE` and failed as
expected after the first successful request while waiting for EOF on the reused
connection:

  not ok ENGINE-RPC-HTTP-PERSISTENT-IDLE-WAIT-OUTLIVES-REQUEST-DEADLINE \
    - HTTP request exceeded the 0.05d0 second deadline
  0 tests passed, 1 failed.

Implementation boundary

The accepted revision retains a 30-second initial/per-request deadline and adds
a distinct 120-second wait for the next request on a reused HTTP/1.1
connection. The idle probe uses PEEK-CHAR, so the first byte remains available
to the normal request parser. Initial silent connections and partial requests
remain under the request deadline. Listener shutdown now waits for the
sequential idle plus request deadlines and the existing five-second margin.

Review and live limit

Independent review found that the first implementation's listener-drain budget
covered only the request deadline. The accepted revision sums the idle and
request deadlines plus the existing margin; the focused drain regression and
full cold-unit layer were rerun after that correction.

At 2026-09-13T12:46:46Z, the active validation deployment was still exact
0c6b51bf, not this revision. It was running without restart or OOM, but its
healer remained incomplete (`frontierWorks=485476`,
`knownIncompleteNodes=371744`, `completed=NIL`), public RPC still returned
`currentBlock=0x0`, and `/data` had 51,557,384,192 bytes available. The preserved
active datadir occupied 55,834,157,056 bytes. A fresh exact-0cffbcb4 datadir
therefore cannot be started safely while preserving the old datadir under the
current capacity. No deployment, restart, datadir reuse, deletion, or other live
mutation was performed.

Conclusion

This closes the deterministic Engine keep-alive deadline defect and provides an
exact verified runtime artifact. It does not provide live Lighthouse validation
of that artifact and does not close SNAP/healer completion, canonical catch-up,
`eth_syncing=false`, shadow, or validator-soak gates.
