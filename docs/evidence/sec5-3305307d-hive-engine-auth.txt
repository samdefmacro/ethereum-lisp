The loader. A full unlimited run counts exactly the 403 test cases; Hive's
per-suite `... test loader` entries are additional result entries that appear

must therefore include each selected suite's loader in `HIVE_EXPECTED_TESTS`.
This is the r26 trap: that focused run passed 6/6 (four named tests plus two
suite loaders) but the broker returned 3 because `HIVE_EXPECTED_TESTS` was set
to 4. That is a runner count mismatch, not a test failure -- and a focused run
can never substitute for one complete 403-item execution.

Why it was not run here

5. The same broker invocation without --prepare-only was run once to record the
   boundary verbatim. It exited 1 before starting anything:

     RUNTIME_PREBUILT=1 RUNTIME_IMAGE=ethereum-lisp-runtime \
       RUNTIME_TAG=sec5-3305307d-amd64 scripts/hive-run.sh --sim ethereum/engine
     exit 1

     Refusing to run hive on macOS.

     Hive must share a host with dockerd: it checks client liveness by dialling
     the container's bridge address on port 8545, which is not routable from a
     macOS host talking to a Docker Desktop VM. It also wants a Go toolchain on
     the host, which this machine deliberately does not have.

     Everything up to the run is done. Use --prepare-only to silence this, and
     run the suite on Linux (.github/workflows/hive.yml does exactly that).

   The second reason is scheduling, not capability. Every retained Engine
   evidence root -- r25, r26, r27, r28, r29 -- lives under
   /data/hoodi-sec5-hive/runs/ on the reviewed remote Linux host. That path
   does not exist on this control plane, and that host is the one carrying the
   protected Section 5 live Hoodi sync. An Engine run there occupies 2 CPUs and
   8 GiB for roughly two hours (r29 ran 19:08:19Z to 21:14:09Z, 2 h 6 min), so
   it is a scheduling decision for the coordinator, not one to take unilaterally
   while the live sync is in progress.
