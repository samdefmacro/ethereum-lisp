Section 5 exit-time memory fault: closing the store before exit(3)

Status

IMPLEMENTED AND VERIFIED LOCALLY (cold unit, integration and e2e; see
"Verification of record"). The node now closes every cached store on every
exit path and then empties RocksDB's shared background pools, before exit(3).
Whether this removes the live exit fault is NOT established: that fault has
only been observed on hour-long amd64 Hoodi runs and has not been reproduced
here (see "Does it reproduce locally?"). What is established is the property
whose absence let it happen -- the process reached exit(3) with the store open
and the pools populated -- and that property is now asserted by tests with
RED controls.

The first revision of this file (9a725cd0) recorded only the reading of the
pinned source. That reading is kept below unchanged except where the fix
proved one of its statements incomplete; that correction is marked.

Revision at which the reading was done: a324d868 (branch
sec5-public-bootstrap-sync), which carries the HTTP keep-alive shutdown fix.

What is already established elsewhere, and is taken as given

docs/evidence/sec5-shutdown-memory-fault-trace.txt records the fault itself:
an SBCL memory fault on pid 1 tid 1 -- the MAIN thread -- in the final phase of
process exit, on three long Hoodi runs (0c6b51bf, 646da589, 5c8a39c0), with the
process still reporting exit 0 afterwards. A later addendum in the same file
resolves the recorded pc, by layout arithmetic against a live /proc/1/maps,
into libc's malloc region, and explains the fault address as
heap_for_ptr(p)->ar_ptr with arena_for_chunk inlined into free -- i.e. free()
of a chunk whose size word carries a spurious NON_MAIN_ARENA bit.

docs/evidence/sec5-shutdown-provenance-audit.txt (Part A) enumerates every
foreign allocation and every explicit foreign free this tree performs and finds
no double, interior or mismatched free anywhere in it. Its A5 finding names the
only exit-time teardown the process provokes: RocksDB's Env::Default()
registers a single static, JoinThreadsOnExit, whose destructor runs under
__cxa_atexit on the calling thread and joins every background thread, then
clears bgthreads_ and so frees each std::thread control block -- chunks
allocated when the pool grew at DB open, early in process life.

Both documents converge on the same prerequisite: the node never closes the
database, so at exit(3) the thread pools are still populated and still running.

What this change is about

Making the node close the store before it exits, on every exit path, so that
the A5 teardown finds nothing of RocksDB's left to tear down.

CORRECTED by the implementation: closing the database alone does NOT achieve
that. The background thread pools A5 names belong to the process-wide
Env::Default(), not to the DB (env/env_posix.cc:220-227 at the pin;
DBOptions::IncreaseParallelism, options/options.cc:698-703, sizes them on the
Env). rocksdb_close unschedules this DB's tasks and waits for its jobs, but the
pool threads stay parked, and JoinThreadsOnExit still joins them and clears
each std::thread vector at exit(3). The change therefore also empties the
pools while the process is alive; see "What changed" below.

Established by reading: the store is never closed from the node

CLOSE-ROCKSDB-KEY-VALUE-DATABASE is defined at
src/foundation/database/rocksdb.lisp:376-384. Its only caller in src/ is
DEVNET-CLI-CLOSE-DB-OPERATOR-DATABASE, src/app/cli/db.lisp:108, which is
reached only from the offline `db` subcommand wrappers. Every other caller in
the tree is a test. Confirmed by grep over src/, tests/ and scripts/ at
a324d868.

The serving node caches its handles in *DEVNET-CLI-KV-DATABASE-CACHE* and its
scope macro's cleanup only rebinds that table; no close, no options destroy.

Established by reading: what the pinned binding exposes today

src/foundation/database/rocksdb.lisp binds, of the shutdown-relevant C API:

    rocksdb_options_destroy           rocksdb.lisp:15

and it does NOT bind rocksdb_cancel_all_background_work, rocksdb_flush,

Established by reading the pinned RocksDB source: what close already does

The pinned archive is tools/rocksdb/rocksdb-11.1.2.tar.gz, root
facebook-rocksdb-9d94571. It was extracted read-only into a scratch directory
and grepped; nothing was built or executed.

    include/rocksdb/c.h:517    void rocksdb_close(rocksdb_t* db);
    include/rocksdb/c.h:788    void rocksdb_flush_wal(rocksdb_t*, unsigned char
                               sync, char** errptr);
    include/rocksdb/c.h:3496   void rocksdb_cancel_all_background_work(
                               rocksdb_t* db, unsigned char wait);

    db/c.cc:1557-1560          rocksdb_close = `delete db->rep; delete db;`
    db/c.cc:8645-8647          rocksdb_cancel_all_background_work =
                               CancelAllBackgroundWork(db->rep, wait)
    db/c.cc:2686-2688          rocksdb_flush_wal = db->rep->FlushWAL(sync)

`delete db->rep` runs DBImpl::~DBImpl (db/db_impl/db_impl.cc:744-765), which
takes closing_mutex_ and, when not already closed, calls CloseImpl -> CloseHelper
(db_impl.cc:527). CloseHelper:

  - sets shutdown_initiated_ and waits for background error recovery
    (db_impl.cc:529-536);
  - calls CancelAllBackgroundWork(false) (db_impl.cc:546);
  - unschedules every task for this DB on all three priority pools
    (db_impl.cc:551-557);
  - WAITS on bg_cv_ until bg_bottom_compaction_scheduled_,
    bg_compaction_scheduled_, bg_flush_scheduled_, bg_purge_scheduled_ and the
    rest have drained (db_impl.cc:562-571);
  - then releases the column-family handles and the rest of the DB state.

Two consequences matter for the fix.

1. rocksdb_close ALREADY cancels background work and waits for it. A separate
   rocksdb_cancel_all_background_work(db, wait=1) binding is the earlier,
   non-destructive half of the same thing; it is useful for splitting the wait
   away from the destructive step (so a bounded wait can be observed and
   reported before anything is deleted), but it is not a prerequisite for a
   correct close. Note that CloseHelper's own wait has NO timeout: a close
   issued while a large compaction is running blocks until that compaction
   finishes.

2. The close is DBImpl's own destructor, so it is idempotent at the C++ level
   only in the sense that `closed_` guards a second CloseImpl; calling
   rocksdb_close twice on the same pointer is a double delete. Idempotence has
   to come from the Lisp side, and rocksdb.lisp:377/383 already provides it by
   guarding on a null handle and nulling the slot.

Established by reading the pinned source: durability at close

DBImpl::CancelAllBackgroundWork (db_impl.cc:482-506) flushes all column
families with FlushReason::kShutDown only when

    !shutting_down_ && has_unpersisted_data_ && !avoid_flush_during_shutdown

has_unpersisted_data_ is set by writes that BYPASS the WAL. This tree never
disables the WAL: there is no rocksdb_writeoptions_disable_WAL binding at all,
and the two write-option objects it creates differ only in the sync flag
(rocksdb.lisp:348 sets sync=1 on WRITE-OPTIONS, rocksdb.lisp:352 sets sync=0 on
BUFFERED-WRITE-OPTIONS).

So the durability statement a close can honestly make on this tree is:

  - every write that returned to the caller is already in the WAL, because no
    write path disables it;
  - a write made through WRITE-OPTIONS (sync=1) was fsynced before it returned,
    and RocksDB's synced write flushes the preceding WAL prefix too
    (as the comment at rocksdb.lisp:349-351 states);
  - a write made through BUFFERED-WRITE-OPTIONS (sync=0) is in the WAL file but
    not necessarily fsynced; closing the DB does not add an fsync for it, and
    does not need to -- it survives a process exit, and is lost only to a host
    or kernel crash, exactly as before this change;
  - closing does NOT flush memtables to SSTs, and does not need to: their
    contents are in the WAL and are replayed on the next open.

Therefore an orderly close changes NOTHING about what is durable. It changes
only whether the background threads and the block cache are released by the
process while it is alive, instead of by a static destructor at exit(3).

What changed

Revision: branch exit-fault-close-store over 9a725cd0:
  68c244b7  database: a RocksDB close happens once, waits for its callers,
            and can empty the pools
  ad6ed0c3  cli: the node closes every cached store when its lifetime scope
            exits
  736ce3ac  ws: a session deregisters its socket, and a hung-up client no
            longer spins
  e0a60850  tests: a real node closes its RocksDB store on SIGTERM, return and
            error exit
  2781311a  database: release the pools only in a process that opened a
            RocksDB store

1. The RocksDB backend (src/foundation/database/rocksdb.lisp).
   - A close is claimed once, by compare-and-swap on a per-handle CLOSING-P.
     A second or concurrent close returns NIL and touches no native pointer.
   - Every native call that takes the rocksdb_t*, and every live iterator
     from creation to its finish, is counted as a user of the handle
     (ROCKSDB-USAGE; increment, full barrier, then read CLOSING-P; the closer
     claims, full barrier, then reads the count). The close waits, bounded by
     +ROCKSDB-CLOSE-DRAIN-SECONDS+ (5 s), for those users to leave, and only
     then calls rocksdb_close and destroys the three option objects. A user
     arriving after the claim signals ROCKSDB-DATABASE-CLOSED-ERROR instead
     of passing a freed or NULL pointer to the C API.
   - A user that outlasts the bound makes the close return :BUSY and leaves
     the handle OPEN and unusable. A leaked handle is the pre-existing exit
     behaviour; a DB freed under a live caller is a fault.
   - The separate rocksdb_cancel_all_background_work binding drafted before
     this revision was dropped: CloseHelper already calls
     CancelAllBackgroundWork(false) first (db_impl.cc:546), so calling it
     beforehand changed nothing.
   - RELEASE-ROCKSDB-BACKGROUND-THREADS (only in a process that opened a
     RocksDB database) sets the LOW, HIGH and BOTTOM pools of
     the default Env to zero threads when no RocksDB database is open, then
     waits up to 2 s for the last rocksdb:* thread to go. Setting a pool to
     zero makes each worker detach itself and pop its std::thread from the
     vector while the process is alive (threadpool_imp.cc, the
     IsLastExcessiveThread branch of BGThread), so JoinThreadsOnExit at
     exit(3) finds empty vectors and frees nothing. Opens, closes and the
     release share one lock, so a release cannot empty pools an opening DB is
     about to rely on; a later open sizes them again through
     IncreaseParallelism and SanitizeOptions.
   - KV-CLOSE is the backend-neutral entry point (types.lisp); the file and
     memory backends take a no-op default.

2. The node (src/app/cli/devnet/files.lisp).
   CALL-WITH-DEVNET-CLI-KV-DATABASE-CACHE closes each distinct cached handle
   exactly once and then releases the pools, in an unwind-protect cleanup, so
   it runs on normal return and on any unwind. It is the innermost scope of
   both the serving node and init. Order on the serving path:
     signal handler -> DEVNET-SHUTDOWN-REQUEST only (unchanged; no store work
       in signal context)
     START-DEVNET-NODE-LISTENERS cleanup -> joins every worker (bounded joins
       terminate and re-join a worker that does not stop)
     DEVNET-CLI-RUN-SERVE-NODE cleanup -> shutdown export, devnet.shutdown
     cache scope cleanup -> close each handle, release pools
     DEVNET-CLI-RUN returns the exit code -> scripts/ethereum-lisp.lisp exit
   A worker that the bounded joins abandoned is covered by (1): the close
   waits for it if it is inside the handle and makes its next call signal.
   Closed handles stay in the table so a straggler gets a signalling handle
   rather than a miss that would reopen the store. A :BUSY or failed close is
   reported on stderr.

3. WebSocket (src/app/cli/devnet/ws-server.lisp). The carried-forward leak is
   fixed: a session removes its shutdown closeable when it ends. Writing its
   test found a worse defect in DEVNET-WS-READ-HANDSHAKE: LISTEN is false at
   end of file and an fd at EOF is always usable for input, so a client that
   hung up before finishing its upgrade request left its session thread
   spinning (wait -> usable -> LISTEN false -> wait) until the node shut down.
   The reader now reads once the fd is usable.

E4 is not changed by this revision: the SIGTERM handler still takes the
closeable mutex and runs closeable thunks in signal context. The store close
was deliberately kept out of it.

Measurements (warm dev image, arm64, this machine)

- rocksdb:* threads in the process with one store open: 10. After closing it:
  still 10 (the close alone does not touch the pools). After
  RELEASE-ROCKSDB-BACKGROUND-THREADS: 0. The info LOG of that store carries
  one "Shutdown complete" after the close.
- WebSocket session of a client that connected and closed without a request,
  on the pre-fix reader: still alive 2 s after the client closed, the process
  consuming 1.01 CPU-seconds per wall second while otherwise idle.

Not verified

- That the live Hoodi exit fault is gone. Owed: an amd64 run long enough to
  have faulted before (above an hour, ~50 GiB datadir), stopped with the
  gate's `docker stop --time 30`, with the exit status, the container log's
  "Shutdown complete" line in chaindata/LOG, and the kernel log checked.

  timeout; CancelAllBackgroundWork makes running compactions abort at their
  next shutdown check, but the time to that check on a 50 GiB store under
  compaction debt is unmeasured, and it now sits inside the supervisor's
  30 s grace period after the export.
- That the pool release completes before exit on amd64 glibc: the wait is
  observed through thread names (/proc/self/task/*/comm), measured here only
  on the arm64 dev image.
- The `db` subcommands close their handle as before but do not release the
  pools; they are offline tools and were not changed.
- E4 (signal-context mutex and closeable thunks) is unchanged.
