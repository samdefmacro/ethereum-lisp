Section 5: the snap tail exited the node on SYNCING

Status

Branch snap-tail-syncing, from 5fee5219 (sec5-public-bootstrap-sync head,
5fee5219678be86ba0ad3e4806526c8a8a4ea8f2). Found, reproduced and fixed
locally. Not deployed, no live run, no cold-all (the coordinator runs it
once at the end).

The cause is not a race with the Engine API. Block 3684909 reads BLOCKHASH
below the snap pivot, and the snap skeleton had never made those blocks
known; the tail then treated the resulting SYNCING answer as a storage
failure, which stops the node.

Revision

  7f079d8f  cli: the snap tail knows the blocks its BLOCKHASH reads, and a
            SYNCING tail block is a phase outcome

================================================================================
2. Mechanism
================================================================================

1. DEVNET-NODE-SNAP-SYNC-PIVOT-ATTEMPT downloads the skeleton from
   anchor+1 = pivot to the target. Nothing below the pivot is a known block
   (the node's own head was 3684026, 840 blocks lower).
2. CHAIN-STORE-BLOCK-HASHES-FOR-HEADER builds the 256-block BLOCKHASH window
   by walking known blocks from the parent; the first unknown ancestor (the
   pivot's parent) ends the walk and every lower number is marked
   :UNAVAILABLE.
3. BLOCKHASH-WORD on an :UNAVAILABLE number signals STATE-UNAVAILABLE-ERROR
   ("BLOCK hash history is unavailable").
4. IMPORT-P2P-BLOCK-CANDIDATE maps STATE-UNAVAILABLE-ERROR for a block that
   is already known (a skeleton block) to SYNCING with no candidate.
5. The tail loop required VALID and called STORAGE-FAIL for anything else.
   STORAGE-ERROR is deliberately not contained by
   DEVNET-NODE-SYNC-COORDINATOR-PASS, so the coordinator thread's outer
   boundary requested a node shutdown: exit 1.

A block N of the tail fails when it reads a block at or below pivot-2,
i.e. deeper than N - pivot + 1, so a contract that reads a fixed older block
fails on the first tail block that executes it.

Candidates from the brief, ruled out:
  (a) Engine busy-guard SYNCING: the tail takes the plain guard (GUARD), not
      the priority guard, and only the priority guard's bounded wait answers
      SYNCING; the import's SYNCING comes from IMPORT-P2P-BLOCK-CANDIDATE.
  (b) parent state not yet visible: in the reproduction block 21 executes
      and its state stays available (asserted by the policy test) while 22
      answers SYNCING, and the one-deep control executes 22 from the same
      parent with the same code.
  (c) the CL's newPayload/fcU: they answered SYNCING for the head, 20+
      blocks above; the reproduction fails with no Engine request involved
      (it sends one only to mirror the live timeline).
  (d) the target moving: TAIL-HEADERS is fixed for the attempt.

go-ethereum holds these ancestors because its skeleton sync fills the header
chain backwards from the head; our bounded skeleton does not.

================================================================================
4. Fix
================================================================================

(i) The cause. DEVNET-NODE-SNAP-BACKFILL-BLOCKHASH-WINDOW runs before the
tail: it walks back from the pivot's parent through known blocks and, if the
window [max(1, pivot-255), pivot-1] is incomplete, downloads the missing
part with EXPECTED-TARGET-HASH set to the hash the pivot's own ancestry names
(the downloader checks hash contiguity across batches, so the whole range is
authenticated from the pivot down). The blocks are collected in memory (at
most 255) and written in one batch by NODE-STORE-EXPORT-SNAP-HISTORY-BLOCKS-
TO-KV: the skeleton's body and receipt checks, contiguity and the terminal
hash re-checked, immutable block/header/receipt records only, no state and
no cursor. Logged as peer.snap.history_backfilled. It runs on every attempt
(also the restart-at-the-pivot path), and costs one guarded walk when the
window is already known.

(ii) The policy. DEVNET-NODE-SNAP-IMPORT-TAIL-BLOCK: ACCEPTED or SYNCING is
logged as peer.snap.tail_retry, the ancestry is refreshed from the live
peers, and the block is imported again, at most *DEVNET-SNAP-TAIL-ATTEMPTS*
(3); then DEVNET-SNAP-TAIL-INCOMPLETE (block, hash, status, attempts). The
coordinator pass contains it as peer.snap.tail_failed and returns NIL, so
the next pass resumes the tail at the first block without state. INVALID
still escapes at once as DEVNET-PEER-SYNC-INVALID (logged
peer.sync.invalid_ancestor by the same pass). A skeleton block that
disappeared is still a storage failure.
