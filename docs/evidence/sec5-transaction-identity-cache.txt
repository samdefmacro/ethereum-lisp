Section 5: a transaction's encoding, hash and sender are derived once per
object, and the chain store keeps the imported objects

Status

Branch wave7-tx-identity-cache, from 05bbd4c5. Transactions are immutable
values now; the canonical encoding, the hash and the sender are computed at
most once per object, and the chain store no longer replaces a block's
transactions with decoded copies. Measured in cold containers; not deployed,
no live run. No cold-all: the coordinator runs it once at the end.

Revision

            sender recoveries
  57b075c2  transactions: immutable values whose encoding, hash and sender
            are derived once

================================================================================
1. Mechanism
================================================================================

The transaction structs were mutable by design (builders and test vectors
wrote their slots), so TRANSACTION-COMPUTATION-CACHE could not be trusted on
its own: TRANSACTION-REFRESH-COMPUTATION-CACHE re-encoded the transaction on
every TRANSACTION-HASH and TRANSACTION-SENDER call and compared the bytes
with the cached encoding before answering. A hit still paid one full
canonical RLP encoding.

The chain store multiplied it. ENGINE-PAYLOAD-STORE-COPY-BLOCK, called when a
block is stored and at every cache, remote-block, invalid-block, prepared-
payload, read-view and transaction-location copy, rebuilt each transaction as
(TRANSACTION-FROM-ENCODING (TRANSACTION-ENCODING TX)): one encoding and one
decode per transaction per copy, and a new object whose hash and sender were
empty. Each RPC lookup of one transaction copied its whole block, so
eth_getTransactionByHash on a 32-transaction block encoded 32 transactions
and recovered the sender of the copy again; forkchoiceUpdated read the stored
copies and recovered every sender a second time (the "Not verified" item of
sec5-txpool-sender-cache.txt).

3. Fix (57b075c2)
================================================================================

- Every slot of LEGACY-, ACCESS-LIST-, DYNAMIC-FEE-, BLOB- and
  SET-CODE-TRANSACTION, of ACCESS-LIST-ENTRY and of SET-CODE-AUTHORIZATION is
  :READ-ONLY; no SETF function exists for any of them. Before the change,
  rg over src/, tests/, scripts/ and docs/ found ten SETF sites on these
  slots, all in tests (including two multi-place SETFs in
  core-chain-store-basic-tests.lisp); each now builds a variant
  (TRANSACTION-FIXTURE-WITH, SET-CODE-TRANSACTION-WITH-FIRST-AUTHORIZATION
  in tests/core-transaction-tests.lisp). No destructive sequence operation
  (SORT, NREVERSE, DELETE, FILL, REPLACE, SETF AREF...) writes into a
  transaction's data vector or lists anywhere in the tree; decoded data is
  a fresh vector (RLP-BYTES-FIELD copies).
- TRANSACTION-COMPUTATION-CACHE (legacy.lisp) holds ENCODING, HASH, SENDER
  and FRONTIER-SENDER, each filled once. TRANSACTION-CANONICAL-ENCODING is
  the per-type encoder (the former TRANSACTION-ENCODING generic);
  TRANSACTION-CACHED-ENCODING fills the slot; TRANSACTION-ENCODING returns a
  COPY-SEQ of it, so no caller can write into the cache. The hash is computed
  from our own canonical encoding, never from received bytes, as before.
- The sender: SENDER is the ungated recovery under the EIP-2 low-s bound (as
  since a1577a56). TRANSACTION-SENDER-FOR-RULES before Homestead used to
  recover a signature the shared recovery refused again, uncached, on every
  call; LEGACY-TRANSACTION-FRONTIER-SENDER now caches that recovery
  (FrontierSigner, no low-s bound) in FRONTIER-SENDER. The signer choice
  (go-ethereum v1.17.6 MakeSigner, as in ff264c42) and every gate (chain id,
  protected-before-EIP-155) read only immutable fields and are applied per
  call, so the cache is keyed by nothing and cannot answer for other rules.
- ENGINE-PAYLOAD-STORE-COPY-TRANSACTION returns the transaction itself and
  ENGINE-PAYLOAD-STORE-COPY-BLOCK shares the block's transaction objects
  (the header, receipts and logs are still copied). The store, the txpool
  reconciliation and the RPC therefore read the hash and sender the import
  derived: one source of truth.

Not changed: every RLP byte, hash, gas value, state, receipt, the wire and
JSON encodings, which transactions are admitted, built or removed. The
txpool's deliberate full copy (ENGINE-PENDING-TXPOOL-COPY, test-observed and
off the import path) still decodes copies.

================================================================================
6. Not verified
================================================================================

- The live effect: nothing was deployed, and the RocksDB direct provider's
  own block reads (which decode from disk per read) were not measured.
- Whether the replay's strict CPU fell: the saving is below the noise of
  the shared Docker VM (section 4).
- In-place writes into a transaction's byte vectors are not refused, only
  absent (no such write exists in the tree); SETF of SLOT-VALUE on a
  read-only structure slot was not probed.
- A block whose transaction list holds something other than a transaction
  was refused by the old store copy (it re-decoded each element); the store
  copy now shares the elements. Import validates the body before storing,
  so no import path reaches the store with one; not separately tested.
- cold-all, cold-e2e and the Amsterdam burn-down were not run (no code
  behind the Amsterdam fork checks changed).
