The invariant

I1: an account-path :TRIE-NODE record implies that every descendant trie node
is durable AND that every non-empty code hash and non-empty storage root named
by every leaf below it is durable.

I1 mentions no state root. That is the whole point: the account trie on disk is
a patchwork of ranges proved against different pivots, exactly as geth's is
(eth/protocols/snap/sync.go:603-606 at 38271784c2b31926563806da9a2e023b88f5e7a8,
v1.17.6-unstable), so any closure claim that mentions a root is void the moment
the pivot moves. A per-node-hash claim is not.

What the writer does

SNAP-SYNC-PREPARE-ACCOUNT-PAGE-RANGE persists nothing at proof time for a store
under the contract. It retains the verified trie and its records on the page
work. SNAP-SYNC-COMPLETE-ACCOUNT-PAGE, after the page's storage and code have
been resolved, persists only the maximal reconstructed subtrees whose whole key
range lies inside the delivered page and all of whose leaves passed a real
durability check. The spine, the boundary proof nodes, the range-straddling
regions and the paths to open accounts are never written at all, which is
geth's rule at sync.go:2453-2476 plus the stack trie's refusal to flush an
unfinished boundary at gentrie.go:316-321.

Two corrections the review forced, both adopted:

  Granularity is per maximal closed subtree at ANY depth, not per depth-four
  bucket. MPT-PROVED-RANGE-CLOSED-SUBTREES keeps descending when a node fails
  and publishes the clean children of a poisoned parent, so one account with
  undelivered storage withholds its own path rather than its bucket's other
  accounts. +SNAP-SYNC-ACCOUNT-SUBTREE-DEPENDENCIES-MAX+ no longer influences
  the write decision at all.

  The qualification predicate is a real durability check, never an inference
  from absence in the page's deferred-storage list. A non-empty code hash must
  name a durable :CODE record; a non-empty storage root must carry this
  client's own whole-root closure proof. That is the standard
  SNAP-SYNC-RANGE-PLAN-FULLY-DURABLE-P and SNAP-SYNC-PROMOTE-COMPLETE-RANGE-PLAN
  already demand, and this file already says twice that completed partition
  cursors are key-space coverage and not closure. A chunked contract therefore
  stays open until the healer publishes its root, which is geth clearing
  needHeal only when the reassembled root both matches and is present
  (sync.go:2272-2282).

Also adopted from the review: the dependency branch of
SNAP-SYNC-CLASSIFY-ACCOUNT-RANGE-SUBTREES no longer records complete
references, so marker absence on the account side stops meaning two different
things.

Why the epoch is not advanced here

The writer and the presence skip are two halves of one contract. A store whose
account spine is withheld cannot run the compensating machinery that exists to
reconstruct closure after the fact: the deferred-storage plan marker,
range-plan promotion and the walk-free completion all open a persisted MPT on
the state root and walk a spine that is deliberately absent. Switching the
writer alone therefore removes the no-rebase acceleration without supplying the
presence skip that replaces it, and it showed up immediately as the newly
merged mid-range-rebase reproduction losing its control arm's 218 promoted
subtrees.

So the writer sits behind *SNAP-SYNC-ACCOUNT-CLOSURE-WRITES*, which the epoch
bump will flip together with the healer rule and the disabling of the three
compensating paths. Its tests set that flag process-globally rather than
binding it, because the production import prepares and completes pages on
worker threads where a LET binding is invisible and the run would silently
exercise the legacy writer.

A defect found while measuring

MPT-PROVED-RANGE-CLOSED-SUBTREES first published nothing at all for any page
narrower than a depth-one bucket. A leaf's stored path carries the hex-prefix
terminator, so its coverage read as 65 nibbles and was rejected by the 64-nibble
bound; only interior nodes could ever be published, and at production task width
the maximal closed subtree IS a leaf. The existing MPT-PROVED-RANGE-SUBTREES is
insensitive to this because it only ever takes the first four or five nibbles of
the coverage. Coverage is now truncated to 64 nibbles. Before the fix a 64-task
import of the fixture published 0 of 24 account leaves; after it, 24 of 24.

The test oracle was unsound (the review's R6)

The memory backend applied a batch by copying the whole table, mutating the copy
and publishing it. That is a read-modify-write over shared state, so two
concurrent writers lost one batch outright rather than reordering it, and three
SNAP buffered applies run without the database write lock. Every batch-inspection
and crash-injection test in this change drives exactly those concurrent writers,
so the oracle could have hidden the defect it was built to find.

KV-APPLY-BATCH on a memory database is now one critical section.

  RED control: with the mutex removed, eight threads writing 64 batches each
  lose keys and MEMORY-DATABASE-BATCHES-ARE-NOT-LOST-UNDER-CONCURRENT-WRITERS
  fails on (ZEROP MISSING). With it, the same test passes.

  A first attempt at a scripted interleaving (intercepting the table copy to
  hold one writer until the other finished) did NOT go red, so it was replaced
  by the real race above. Recorded because it looks like a stronger control and
  is not one.

The compensating machinery is disabled, not merely unreachable

The plan-marker write and SNAP-SYNC-PROMOTE-COMPLETE-RANGE-PLAN are gated on
the writer seam. SNAP-SYNC-FILL-STORAGE-THEN-HEAL's walk-free completion had no
guard of its own: it was unreachable only because its predicate reads a plan
marker that is never written for such a store, so dropping either of the other
two gates would have re-opened a path that publishes a state root without
traversing the trie. It now refuses explicitly.

SNAP-SYNC-RANGE-PLAN-FULLY-DURABLE-P is deliberately NOT gated. It answers a
question about the plan; the guard belongs at the site that acts on the answer.

  SNAP-CLOSED-ACCOUNT-STORE-NEVER-PROMOTES-A-RANGE-PLAN pins it. Control: with
  the legacy writer, promotion gets past the marker check and goes on to open a
  persisted MPT on the state root, which the synthetic store does not hold, so
  it signals -- reaching that walk is the proof that nothing but the guard keeps
  the closed-writer arm out of it. Subject: under the closed writer it returns
  zero without touching the store.

Every storage ingestion path meets the uint256 ceiling

The 33-byte ceiling is what keeps account and storage nodes disjoint in the
kind-blind trie-node table, and contract storage is attacker-controlled on a
public network, so it has to be enforced at ingestion rather than assumed from
the protocol. SNAP-SYNC-STORAGE-ENTRIES applies SNAP-SYNC-STORAGE-TRIE-VALUE to
every StorageRanges response, which covers the complete-group, byte-capped and
partitioned large-storage paths on both the single-source and multi-source
importers, and the snap/1 server uses the same function.

A storage leaf reached by HASH during healing did not pass through it. That
path now applies the same bound where the node is decoded, fail-closed in both
directions: a peer supplying an over-wide storage leaf is a protocol fault, a
stored one is storage corruption.

  SNAP-HEALED-STORAGE-LEAF-VALUE-MEETS-THE-UINT256-CEILING pins the bound and
  its rejections, including that an account leaf value can never pass it, which
  is the disjointness argument stated as an executable check.

Kind-blindness

The flat :TRIE-NODE table holds account and storage nodes in one
content-addressed space, so a kind-blind presence rule needs the two node sets
to be disjoint. Pinned by
SNAP-ACCOUNT-AND-STORAGE-TRIE-NODES-CANNOT-COLLIDE:

  The shortest account leaf value is 70 bytes, derived from the encoder rather
  than assumed: RLP([0, 0, emptyRoot(32), emptyCodeHash(32)]).
  The longest storage leaf value is 33 bytes, and that ceiling is ENFORCED on
  peer input by SNAP-SYNC-STORAGE-TRIE-VALUE, which the test exercises in both
  directions. A leaf node is RLP([path, value]), so equal leaf encodings have
  equal values, and the ranges do not overlap.
  No account-trie node is ever inlined: every record of a real account trie
  encodes to at least 32 bytes, so account nodes are always hash-addressed.
  Without this the branch/extension induction does not close, because a storage
  branch may carry an embedded child where an account branch carries a hash.
  Over real tries the two hash sets are disjoint, with a positive control that
  the disjointness check can report a collision.

Crash injection (step five)

SNAP-ACCOUNT-CLOSURE-SURVIVES-A-CRASH-BEFORE-THE-ACCOUNT-BATCH drops the first
account-node batch that follows a storage batch; SNAP-ACCOUNT-CLOSURE-SURVIVES-
A-CRASH-BEFORE-THE-CURSOR-BATCH drops the synchronous progress batch after an
account-node batch. Both assert the crash actually fired, that the store then
holds no account node whose closure it lacks, and that the resumed import
converges and installs the authorized root.

(client.lisp:7613 to the account batch) and code (client.lisp:8060-8062 to the

SNAP-ACCOUNT-CLOSED-SUBTREE-FOLLOWS-ITS-DEPENDENCIES is the batch inspector the
plan asked for, and it runs over BOTH the single-source path and
SNAP-SYNC-IMPORT-STATE-MULTI with two sources, so the cross-thread code and
storage writers are exercised. For every account trie-node put in every applied
batch it requires every descendant node, every non-empty code hash and every
non-empty storage root named by a leaf beneath it to be durable in that batch or
an earlier one. Its positive control writes the account root alone into a fresh
store and requires the inspector to report violations; its counters
(inspected, account leaves, code checks, storage checks) all have to be
non-zero, so a run that inspected nothing cannot pass.

The open questions the plan asked to settle

Q1, is the storage batch always applied before the account batch on the multi
path: yes, but not for the design's stated reason, and the guarantee is weaker
than the design assumed. Inline storage is applied on the page's own thread
before the account batch. Chunked storage is applied by the committer thread and
the runtime mutex supplies the happens-before edge. Codes are NOT in the account
batch on the production path at all: SNAP-SYNC-MULTI-FETCH-PAGE-CODES returns
the empty list on every exit and code is written by the code worker's own batch;
the page learns of it only by re-reading the store. The design's "codes ride in
the same batch" is false, and the ordering rests on read-observes-write plus a
single WAL. This change stops depending on the claim either way: the writer
re-reads the code table at classification time and an account whose code is not
durable is simply open.

Q2, is buffered-batch order a total order that survives a crash: yes on RocksDB
-- one handle, no column families, one WAL, atomic batches, suffix-only loss,
and the range cursor is published with the synchronous apply that fsyncs the
preceding prefix -- and it was NOT true of the in-memory backend the tests use
as the crash oracle until this change fixed it.

================================================================================
Phase two: the non-snap writers, read out of the tree
================================================================================

Phase one classified the non-snap writers in prose. Epoch seven makes account
presence load-bearing, so each one is re-read here as a mechanism, with the
question stated the way it has to be answered: for THIS caller, is the whole
dirty set plus the code it names applied in ONE atomic batch -- in which case
I1 holds iff the base state was already closed -- or in several, in which case
order and crash behaviour decide it?

The mechanism that makes the question sharp

MPT-POPULATE-DIRTY-BATCH (src/foundation/trie/persistence.lisp:419-437) adds
(MPT-DIRTY-NODES TRIE) and nothing else. MPT-PERSIST's own docstring at :444-449
states the consequence: "For a trie opened from a persisted root, untouched hash
subtrees are never resolved or rewritten." A dirty-node batch is therefore a
closed subtree only when every hash child it names was ALREADY durable. That is
the exact shape of an I1 violation for a non-snap writer, and no marker, proof
or provenance bit distinguishes such a node from one the closed snap writer
wrote: the :TRIE-NODE table is content-addressed and kind-blind.

Callers, enumerated from the tree

(a) Genesis export: sound as it stands, for a reason worth pinning

The scheme marker is stamped by its own batch inside
SNAP-SYNC-ENABLE-COMPLETE-NODE-SCHEME-P (client.lisp:893-904), called from
src/app/cli/devnet/persistence.lisp:539-552 deliberately BEFORE the export. Two
batches, in that order. The review reads this as the marker certifying only
"the store was empty at datadir creation", which is true and is exactly what
makes it safe here:

  - :897 stamps only when SNAP-SYNC-TRIE-NODE-STORE-EMPTY-P (:883-891) holds,
    so a crash between the marker batch and the export batch leaves a marked
    store with an EMPTY :TRIE-NODE table. I1 is vacuous there, and the next
    start re-enters the same path.
  - the export batch is a single atomic write carrying the whole materialized
    trie AND the code it names. A crash loses all of it or none of it. A
    partial genesis trie is not reachable through this path.

So the smallest sound change at the genesis site is NO change. What is missing
is that the soundness rests entirely on "one batch", and nothing in the tree
says so: splitting the export for memory reasons would silently void I1 while
every existing test stayed green. That is what the new regression pins.

(b) Block commits over an incomplete state

Mechanically the hazard is real: a dirty-only commit writes new parent nodes
above hash children it assumes durable. What makes it unreachable is that
execution needs the parent state, and the snap path refuses to execute until
the import reports completion -- src/app/cli/devnet/dialer.lisp:2272-2275
signals "Snap pivot state import returned before completion" and only then
installs the forkchoice sync pivot (:2279-2292) and executes the bounded
post-pivot tail (:2293-2325), each tail block required to return VALID.

That is an orchestration argument about one call path, not a property of the
writer, and epoch seven must not rest on it. Stated as an induction it is
honest: genesis writes a complete state in one atomic batch, a snap sync
publishes its root only through the healer's post-order contract, and every
block commit preserves closure if its base had it. The base cases are the two
this change is about; the step is the block commit.

(c) The snap/1 server is the one that does not fit

SNAP-SYNC-ROOT-TRIE (src/networking/snap-sync/backend.lisp:18-30) calls
(MPT-PERSIST DATABASE TRIE) on (STATE-DB-STATE-TRIE STATE) -- the ACCOUNT trie
alone. Not the touched storage tries, not the code. It is not a complete-state
commit and does not have the atomic-batch-of-everything property the other
three callers have, and peer-sync keeps it live while we are ourselves syncing.
This is the writer that needs a change rather than a comment; it is recorded
here before the fix so the reasoning survives the diff.

What changed

+SNAP-SYNC-COMPLETE-NODE-SCHEME-VALUE+ is #(7). #(6) is recognized and never
trusted (+SNAP-SYNC-ACCOUNT-WALK-COMPLETE-NODE-SCHEME-VALUE+), so an epoch-six
datadir opens, keeps its content, is revoked by SNAP-SYNC-LOAD-PROGRESS like
every earlier epoch, and resyncs. Without that entry an unrecognized marker is
a storage failure and every existing datadir would refuse to open; the RED
control below is exactly that.

*SNAP-SYNC-ACCOUNT-CLOSURE-WRITES* defaults to true. It remains the one seam:
the healer takes the account skip only when SNAP-SYNC-CLOSED-ACCOUNT-WRITES-P
holds for the store, read once per traversal, so the skip can never be taken
over account nodes the legacy writer put.

INTEGRATE-PRESENT-WORK skips a durably present, unmarked, unfetched account
node without descending. The leaf-length disjointness argument sits at the skip
site: equal leaf encodings have equal values, account leaf values are >= 70
bytes, storage leaf values <= 33 bytes and that ceiling is enforced at every
ingestion point including the healed storage leaf, and no account node is ever
inlined, so a hash reached along an account path names an account node.

The writer count is three, not two as phase one recorded. The healer's own
fetched-node flush in %SNAP-SYNC-HEAL-STATE also puts account-path :TRIE-NODE
records; the snap-server-closure change found it (fc0bb2ea, evidence file
sec5-snap-server-closure.txt, "the healer site"), measuring with the
marker-blind batch audit a parent put one batch before its child. It writes
top-down, each node with its incomplete marker in the same batch, and deletes
the marker only at the node's post-order :NODE-COMPLETE sentinel, which drains
deferred storage and flushes code first. So for this writer I1 holds only as
"present AND unmarked", and that is the rule: INTEGRATE-PRESENT-WORK processes
a marked node in the branch ahead of the presence skip, and the durable marker
is read with the node on every local read under the scheme. This is the
epoch-six storage rule, unchanged; the skip site now says why its order
matters.

SNAP-EPOCH-SEVEN-HEALER-DESCENDS-A-MARKED-ACCOUNT-NODE-AFTER-A-CRASH pins it
across a crash. A 2,048-account trie (2,709 account nodes) is healed into an
epoch-seven store whose source dies after three GetTrieNodes responses; the
flush has left the root and three nodes below it, all four marked, and the
rest absent. The healer is re-entered from the root, as after a pivot rebase
(which deletes the heal checkpoint). Subject: it descends the marked root,
fetches exactly the 2,705 missing nodes and completes over all 2,709. Control,
in the test: the same store with the four markers deleted -- what a
presence-only skip sees -- completes with zero fetched and four of 2,709
nodes present, a false completion. RED (R7 below): with the durable marker
read blinded, the subject arm fetches nothing and fails.

One source fix fell out. SNAP-SYNC-BUFFER-ACCOUNT-PAGE-CONTENT applied an empty
buffered batch for a closed-writer page that closes nothing (every node
straddles its bounds or sits above an open account). The legacy writer never
produced one, because it always had markers to write. It now skips the apply.
SNAP-STATE-IMPORT-BATCHES-COMPLETE-STORAGE-TRIES has always required every
buffered batch to be non-empty and went red on this before the fix.

Step 6: the non-snap writers
(SNAP-EPOCH-SEVEN-DOES-NOT-TRUST-ACCOUNT-NODES-WRITTEN-BY-BLOCK-IMPORT)

The test drives the shipped writers: NODE-STORE-EXPORT-TO-KV for genesis,
COMMIT-STATE-DB-TO-CHAIN-STORE plus NODE-STORE-EXPORT-FORKCHOICE-TO-KV for two
blocks. Genesis holds 300 accounts, twelve with code and storage; each block
creates twenty contracts and writes a slot into an existing one. The epoch is
stamped on the empty store immediately before the genesis export, where the
devnet datadir stamps it. Every applied batch is audited for I1.

  audit of the shipped writers: 526 account nodes inspected (412 of them
    genesis, so the block commits were seen), 2,429 leaf checks, 280 code and
    280 storage checks, no violation; SNAP-CLOSURE-STORE-VIOLATIONS empty.
  a store that took the same nodes before the contract was offered: cannot
    enter the epoch.

So the marker certifies "empty at creation", and that is enough: after the
stamp the genesis export is one atomic batch carrying the trie and its code,
and each block commit is one batch of dirty nodes plus that block's code over
a base already closed. The test establishes that for these two writers by
audit, not by argument.

Not covered by it, and needed for the argument to be complete: the snap/1
server's SNAP-SYNC-ROOT-TRIE (src/networking/snap-sync/backend.lisp) calls
MPT-PERSIST on the account trie alone, without its storage tries or code, into
the database it serves from. On an epoch-seven store that can put a present,
unmarked account node whose storage is not durable, which the healer would now
skip. That writer is owned by another change and is not touched here.
