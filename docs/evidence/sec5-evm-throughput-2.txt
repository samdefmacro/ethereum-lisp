================================================================================
2. Changes
================================================================================

61c210bb (interpreter/interpreter.lisp, base.lisp, opcodes.lisp,
opcodes/arithmetic.lisp, execute.lisp): %RUN-EVM-MACHINE-IN-REGISTERS holds
PC, SP, the stack vector and the regular gas left in locals and runs
PUSH0-PUSH32, DUP, SWAP, POP, JUMPDEST, JUMP, JUMPI, PC, GAS, ADD, SUB, LT,
GT, EQ, ISZERO, AND, OR and XOR inline, charging each instruction's base gas
first and failing with the step loop's messages at the step loop's points
(out of gas before any counter moves, underflow, overflow at 1,024, invalid
jump). The word operations (WORD-ADD ...) are defined once in base.lisp and
the family handlers use the same functions. Gasless frames, step-budgeted
frames and a regular gas budget above the fixnum range keep STEP-EVM-MACHINE.

cbafc77f: WORD reduces with LOGAND 2^256-1 instead of MOD (the same modulus
for every integer, negatives included; 200,000 reductions of a 511-bit
product 10.1 ms -> 1.9 ms; LDB was slower than MOD).

ccd0bf1a: the JUMPDEST bitmap is computed once per code vector (a weak,
synchronized EQ table; state objects share code vectors and nothing modifies
them) instead of on every frame entry.

5bd780b3 (state/db.lisp, state/types.lisp): a storage write journals its one
slot (value, zero mark, the storage-trie root wrapper, the memoized storage
root), an account change the account record, a touch nothing; the undo writes
that back into the object the later undos have restored. Object creation,
deletion and code changes keep the whole-object clone. A slot read after a
journal entry now keeps its cached backing value through a revert, which is
correct (it is the backing value) and is what go-ethereum's originStorage
does; the 3684027 read-after-journal regressions still pass. The replay's
per-block "slots" count (the slots our post-state knows, compared one by one
with the reference) rose in 9 blocks for that reason, all still matching.

295a758f: no UNWIND-PROTECT in the loop; every exit stores the registers
itself. The per-frame instruction counter nothing read is gone. Burner frame
3.1 -> 2.3 ms.

f574325b (foundation/bytes.lisp): BYTES-TO-INTEGER takes seven bytes at a time
past eight bytes (32 bytes: 0.93 us / 2,480 bytes consed -> 0.15 us / 384).

8ae6b113 (evm/conversions.lisp): WORD-TO-HASH32 / WORD-TO-ADDRESS write a
fixnum's low eight bytes and a wider word 32 bits at a time (256-bit word:
0.70 us / 1,408 bytes -> 0.23 us / 448).

5068bbb1: the register loop no longer calls handlers; see section 3.

Tried and dropped, each measured without a gain on real blocks: a journal
for the EVM access sets instead of copying them per call (0% CPU on 20
blocks), a range tree instead of the opcode comparison chain, a derived
instead of an accumulated charged-gas counter, hoisting the base-gas table
into a local, MLOAD/MSTORE inline when memory need not grow (memory loop
47.8 -> 40.9 ms, no change on 33 corpus blocks), reusing the Keccak digest
object (12% of one 32-byte hash).

================================================================================
3. The regression fixed on the branch: 1,024 CALL levels and the stack
================================================================================

Symptom: at 8ae6b113 the EEST state gate
(OPTIONAL-PHASE-A-EEST-STATE-TEST-ROOT-VECTORS-EXECUTE) died twice, both
runs "fatal error encountered in SBCL ... maximum interrupt nesting depth (8)
exceeded / Bad frame pointer", container exit 1, no test result. A third run
with the JUMPDEST cache disabled died the same way.

Mechanism: the register loop called every non-inline handler from inside its
own frame, CALL included, so each nested CALL level carried the loop's frame
on top of the step loop's. Measured with a self-CALL contract
(0x5f5f5f5f5f305af100, all gas forwarded) and the stack pointer at each
frame's creation: 1,840 control-stack bytes per level at 3c0cfeab, 2,016 at
8ae6b113. 1,024 levels need 1.88 MB at the base and 2.06 MB at 8ae6b113; a
default SBCL thread stack is 2 MB. In a fresh default thread the recursion
returns :STOPPED at 3c0cfeab and exhausts the control stack at 8ae6b113.

Fix (5068bbb1): the loop stores its registers and returns at any instruction
that needs a handler; RUN-EVM-MACHINE, inlined into %EXECUTE-BYTECODE-FRAME,
runs it (EXECUTE-OPCODE when the loop charged the base gas, STEP-EVM-MACHINE
when the fork decides it) and enters the loop again, keeping only the
machine live across the handler: 1,840 bytes per level again. (At the base
a level is five frames of 136, 120, 200, 808 and 576 bytes: the frame
function with the step loop, EXECUTE-SYSTEM-OPCODE, EXECUTE-EVM-MESSAGE-CALL,
EXECUTE-MESSAGE-CALL-CHILD and its TRACED-BODY; 8ae6b113 added the loop's
144-byte frame and RUN-EVM-MACHINE's 32, and the frame function grew from 136 to 192 bytes when the loop
was first inlined into it with its locals live across the handler call.)

Regression test: EVM-SELF-CALL-REACHES-THE-DEPTH-LIMIT-ON-A-DEFAULT-STACK
(unit) runs the recursion in a fresh default-stack thread, its body handling
every condition. RED: the same code at 8ae6b113 reports
:CONTROL-STACK-EXHAUSTED (warm probe); GREEN at 3c0cfeab and 5068bbb1.

Note: 1,840 bytes per level is 92% of a 2 MB stack at depth 1,024 at the base
already; see "Out of scope".

Out of scope, seen on the way
================================================================================

- A CALL level costs 1,840 bytes of control stack at the base and here, so
  1,024 levels use 1.88 MB of a default 2 MB thread stack. Any frame added on
  the CALL path, or a thread started with a smaller stack, fails real
  deep-recursion transactions; the new depth test guards the default case.
- Lazy flat-loader storage (a STORAGE-LOADER without the account's entries
  preloaded): a storage-root computation caches a trie of the loaded slots,
  which later reads consult instead of the loader. The durable provider uses
  storage tries and the memory/file oracle preloads every entry, so neither
  is affected; the journal oracle test uses tries for that reason.
- The BN254 pairing and multiplication precompiles are pure Lisp with a
  recursive extended-Euclid inverse (46 us a call; one pairing 61 ms).
- tests/hoodi-replay-tests.lisp compiles with a full WARNING "This is not a
  REAL: NIL" at the base already.
- The warm image logs the known style-warnings (PRECOMPILE-P unused in
  call.lisp; &OPTIONAL with &KEY in execution/state.lisp and two txpool
  functions).
