Section 5: the six-second newPayload CPU is EVM interpreter throughput on
Hoodi gas-burner blocks

Status

Branch np-six-second-cpu, from a07c912e. FOUND, REPRODUCED LOCALLY, FIXED
(about 6x). The near-constant 5.6-6.4 s of npExecuteCpuMs in the R4 run
(hoodi-el-sec5-b5161312, revision b5161312) is not an initialisation, a cache
miss, GC or waiting: it is the EVM interpreter executing one contract. Most
Hoodi blocks in the executed range are filled to the 60M gas limit by 20-24
transactions to a gas burner at 0x6b3f1c2aa4f0a2a49bb782a4e83db5a0764326ec
(2,490,015 gas each). One such transaction cost 250 ms of CPU and 45 MB of
garbage in the interpreter (arm64 dev image; the live amd64 figure is the
same, 6.0 s / 24). After the fix the same frame costs 40 ms and 9 MB, so a
full burner block should cost about 1 s instead of 6 s. That is still not
"well under a second"; see "Next".

Not deployed; no live run; no cold-all (the coordinator runs it once).

1. What the slow blocks are
================================================================================

Data (read-only): `docker logs -t hoodi-el-sec5-b5161312` on the Hoodi host
(208 engine_newPayloadV4 lines with npExecuteMs, 00:26:08Z-01:33:42Z on
2026-09-24), and block bodies/receipts for 3683690-3684040 from public Hoodi
JSON-RPC (rpc.hoodi.ethpandaops.io, ethereum-hoodi-rpc.publicnode.com), because
the R4 container was OOM-killed at 02:25:29Z (see "Out of scope").

Hoodi block gas alternates between ~60M (the limit) and ~0.2-5M. The full
blocks are the burner: block 3683733 (timestamp 00:26:00Z) carries 24
transactions to 0x6b3f...26ec, each with gasUsed 0x26029f = 2,490,015
(eth_getBlockReceipts). In the executed range 3683701-3684026 (326 blocks,
snap target 3683701 at 00:24:14Z, EL head frozen at 3684026 = 01:31:12Z):

  burner transactions per block   0: 154 blocks   10-11: 3   17: 2   19: 2
                                  20: 3   21: 5   22: 34   23: 67   24: 56

The burner's code (eth_getCode, latest):
  0x5f5a5f600e565b5f5260205fa1005b6127105a1060065760010161133750600e56
  = PUSH0 GAS PUSH0 PUSH1 0e JUMP; 06: JUMPDEST PUSH0 MSTORE PUSH1 20 PUSH0
    LOG1 STOP; 0e: JUMPDEST PUSH2 2710 GAS LT PUSH1 06 JUMPI PUSH1 01 ADD
    PUSH2 1337 POP PUSH1 0e JUMP
i.e. a 12-instruction, 44-gas loop until less than 10,000 gas is left: about
56,000 iterations and 680,000 instructions per transaction, about 16M
instructions per full block. Nothing in it touches state, precompiles or
memory beyond one word, which is why npTrieNodeReads (9-1126) and GC
(26-53 ms) are unrelated to the cost.

Correlation. newPayload start = log time - handlerMs - readMs, matched to the
latest not-yet-matched block whose timestamp precedes it. The first five are
unambiguous (Lighthouse delivered them in slot order):

  log time (Z)  start-slot  block     gas used     burner txs  npExecuteCpuMs
  00:26:08      +2.3 s      3683733   59,995,410   24          6028
  00:26:25      +0.6 s      3683734    1,181,733    0            72
  00:26:59      +2.4 s      3683735   59,655,905   22          5710
  00:27:13      +11 s       3683736    1,487,217    0           100
  00:28:02      +2.1 s      3683739   59,488,933   22          5768

After that Lighthouse re-sends old blocks after its 30 s timeouts and the
time match is no longer one-to-one, so the rest is argued from populations:
112 of the 208 executions took more than 1 s of CPU; the sorted CPU values
have exactly the shape of the burner histogram, including the rare partial
blocks: three at 2903/2932/3021 ms (the three 10-11-burner blocks at
~250 ms each), four at 4463-5200 ms (17-20 burners), and the 24-burner mass at
5.6-6.3 s. Everything else is 5-617 ms. So: ~250 ms of CPU per burner
transaction, on the live amd64 host.

================================================================================
3. Fix
================================================================================

src/runtime/evm/opcodes.lisp: the schedule is unchanged and renamed
%OPCODE-BASE-GAS-BY-SCHEDULE. OPCODE-BASE-GAS reads *OPCODE-BASE-GAS-TABLE*,
computed once from that schedule, for every opcode outside
+CONTEXT-DEPENDENT-BASE-GAS-OPCODES+ (BALANCE, EXTCODESIZE, EXTCODECOPY,
EXTCODEHASH, CREATE, CALL, CALLCODE, DELEGATECALL, CREATE2, STATICCALL,
SELFDESTRUCT: the only branches of the schedule that read the context), and
calls the schedule for those eleven.

src/runtime/evm/interpreter/interpreter.lisp, opcodes/*.lisp,
interpreter/machine.lisp: the dispatch, the five handler families and
EVM-MACHINE-CHARGE-GAS declare MACHINE an EVM-MACHINE and the opcode an
(UNSIGNED-BYTE 8), so the (= op #x..) chains and the WITH-SLOTS accesses
compile inline.

src/runtime/evm/gas.lisp: EVM-GAS-BUDGET-CHARGE-REGULAR updates the budget
directly. With a zero state cost EVM-GAS-BUDGET-CHARGE can afford exactly
when amount <= regular, spills nothing, leaves the (non-negative) state
reservoir and the used-state/spilled counters unchanged; the new body does
exactly that without allocating an EVM-GAS-COSTS.

src/runtime/evm/base.lisp: WORD returns a non-negative fixnum unchanged
instead of calling the bignum MOD (its value mod 2^256 is itself).

No gas value, opcode semantics or result shape changed.

================================================================================
5. Next
================================================================================

~1 s per full burner block (estimate: 24 x 40 ms on arm64; amd64 matched
arm64 before the fix) still holds the store guard for one second per block
and leaves little headroom in a 12 s slot once forkchoiceUpdated's own
~2.9 s canonical phase (below) is added. The remaining interpreter cost is
spread: the list stack (16 bytes per push), generic arithmetic on PC and gas
counters typed (INTEGER 0 *), and the closure per comparison. A vector stack
with fixnum fast paths is the next step and needs the EEST gates again.

The same cost explains the long store-guard holds in the R4 log
(node.store_guard.long_hold, 00:20-01:40Z): forward-batch-import 5,772-6,728 ms
(one burner block per hold) and the snap forward importer
(ethereum-lisp-devnet-sync-coordinator) 5,608-6,500 ms before target
completion, and engine_newPayloadV4 2,952-6,424 ms.
