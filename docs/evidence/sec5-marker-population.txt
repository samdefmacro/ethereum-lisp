Section 5 marker population: where the healer's stale markers come from

Status

marker that survives the range phase is written by a StorageRanges partition
of a byte-capped contract, and every one is stale. The range phase now
publishes a chunked trie's whole-root proof and clears those markers when its

Method

tests/snap-marker-population-tests.lisp wraps every site that can write a
marker and binds the site name for its thread: the first byte-capped storage
page (SNAP-SYNC-POPULATE-VERIFIED-STORAGE-GROUP, partial arm), a whole
single-response group (same function, complete arm), a partition page
(SNAP-SYNC-BUILD-STORAGE-PAGE-BATCH, both importers), the legacy account
prebuffer (SNAP-SYNC-PREPARE-ACCOUNT-PAGE-RANGE), the account page
(SNAP-SYNC-BUFFER-ACCOUNT-PAGE-CONTENT), the healer (%SNAP-SYNC-HEAL-STATE) and
the new closure step. SNAP-SYNC-POPULATE-INCOMPLETE-NODE-BATCH and
SNAP-SYNC-DELETE-INCOMPLETE-NODE-BATCH count puts and deletes per site and
remember each marked hash's last writer. At SNAP-SYNC-HEAL-STATE entry the
durable marker set is read and each marker is judged against the store as it
stands then: STALE when the node and its whole trie-node closure are present,
GENUINE when anything beneath it is absent. The owning trie is read off the
completed store; :CURSOR-SET means a StorageRanges cursor set exists for that
exact root.

Fixture: 300 accounts, every fifth a contract with code and one to six slots
(answered whole by one response), plus two contracts of 2,500 slots that the
byte cap partitions. Byte limit 30,000 (8,000 for the rebase arms, so the
account range has pages to rebase between). Production publication depths
(four and five nibbles). Fresh memory store, so the closed account writer and
the account presence skip are on.

Why they survive

A partition page marks every record not inside a subtree it proves whole
(SNAP-SYNC-INCOMPLETE-RECORD-HASHES over MPT-PROVED-RANGE-SUBTREES), and that
proof is only ever issued for subtrees whose pointer path is at least four
nibbles deep. So the top four levels of every chunked trie are always marked,
and for a trie of a few thousand slots, whose leaves sit at depth three or
four, nearly all of it is. The page that wrote a spine node cannot clear it,
because the node straddles the page; no later page names it complete, because
it straddles that page too. Nothing else on the range path deletes a storage
marker. The healer then processes every one (present and marked is never
skipped), which is the live walk: at 215 nodes/s, hours.

Decision per site

  first byte-capped page, partition pages: stale markers on complete content,
    the spine above proved subtrees. Completeness is provable at write time,
    so the range phase now closes the trie (below).
  whole single-response group: writes no marker, publishes the root proof.
    Unchanged.
  account prebuffer and account page: write markers only for a legacy store.
    Unchanged; the account-side rules were not touched.
  healer fetched-node flush: genuine until the node's post-order sentinel,
    because its children may be absent. Unchanged.
  mid-range rebase: carries no marker of its own. A root that moves before its
    cursor set completes never gets the step (markers stay, fail-closed); the
    new root's cursor set downloads it again and its closure walk clears the
    shared nodes' markers, each after verifying that node's closure.

geth's rule (eth/protocols/snap/sync.go:2272-2282 at
38271784c2b31926563806da9a2e023b88f5e7a8, v1.17.6-unstable): when every
storage subtask of a chunked contract is done, needHeal is cleared only if the
reassembled root matches and is present. The local equivalent follows.

The change

SNAP-SYNC-PUBLISH-STORAGE-ROOT-CLOSURE, called by SNAP-SYNC-FILL-STORAGE-ROOT
(now a wrapper over the renamed %SNAP-SYNC-FILL-STORAGE-ROOT-RANGES) after the
cursors complete, and by SNAP-SYNC-MULTI-FILL-STORAGE-ROOT before a waiter
returns to its account page. It publishes the :STORAGE-ROOT proof and deletes
the markers of the nodes it walked, in one buffered batch, only when:

  - the store is under the current closure contract (a legacy store returns
    :LEGACY-STORE and keeps its behaviour);
  - all sixteen cursors of the set keyed by (account, STORAGE-ROOT) are
    completed and their ranges tile [0, 2^256-1]; a set is keyed by its storage
    root and every page is verified against that key, so there is no second
    root to mix in;
  - a walk from STORAGE-ROOT, stopping only at this client's own :STORAGE
    subtree proofs, finds every node present and matching its hash, and every
    storage leaf within the uint256 ceiling. Marker absence is not trusted by
    the walk: an unmarked node is descended like a marked one.

Content addressing makes the walk the proof that matters: a node written under
another root or another trie is used only because its hash is the one this
root names, and nodes are never deleted from the table. Any refusal writes
nothing. The walk is bounded by *SNAP-SYNC-STORAGE-ROOT-CLOSURE-MAX-NODES*
(1,048,576); past it the step refuses and the healer walks the trie as before.

A consequence on the account side, through the unchanged predicate

The closed account writer already treats a storage root as closed iff its
:STORAGE-ROOT proof is durable. Because the multi-source waiter publishes it
before returning to the account page, a chunked contract's account leaf is
now normally closed when its page completes, and its path is written instead
of withheld. The ordering is the existing one: the proof batch is buffered
after the completing storage batch and before the account batch on the same
WAL, and the account cursor's synchronous apply fsyncs the prefix.
