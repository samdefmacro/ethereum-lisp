optional-phase-a-eest-blockchain-rlp-replay-executes ended with

The throughput branch's own depth test reproduces it on the base tree:

  cl-workbench validation run cold-unit \
    --match EVM-SELF-CALL-REACHES-THE-DEPTH-LIMIT      (at 7cef5a67)

  fatal error encountered in SBCL pid 11 tid 13:
  maximum interrupt nesting depth (8) exceeded
  Bad frame pointer 0xffff835c0010 [valid range=0xffff833e0000..0xffff835e0000]

The valid range is 2 MiB, the default thread stack. The test body handles
STORAGE-CONDITION, but SBCL 2.2.9 never gets that far: the process dies, so
the test (and every test after it in the run) reports nothing. That is why a
gate crashes rather than fails.

================================================================================
2. Mechanism: bytes per CALL level
================================================================================

Measurement: a self-CALL contract (0x5f5f5f5f5f305af100: PUSH0 x5, ADDRESS,
GAS, CALL, STOP; all gas forwarded) started at depth 960 in a fresh thread,
with MAKE-CHILD-EVM-CONTEXT wrapped to record the stack pointer
(SB-KERNEL::CURRENT-SP) each time a level makes its child's context.  The
wrapper is a leaf called from the frame about to run the child, so it adds
nothing between levels; every consecutive difference was identical.  Frame
sizes from the debugger's frame pointers (SB-DI) at the same point.  arm64,
SBCL 2.2.9, warm dev image.

  7cef5a67, one CALL level = 1,968 bytes:
    %EXECUTE-BYTECODE-FRAME (run-evm-machine inlined)        136
    EXECUTE-SYSTEM-OPCODE                                    120
    EXECUTE-EVM-MESSAGE-CALL                                 224
    EXECUTE-MESSAGE-CALL-CHILD                               896
    (FLET TRACED-BODY :IN EXECUTE-MESSAGE-CALL-CHILD)        592

  The throughput record (sec5-evm-throughput-2.txt section 3) measured the
  same five frames at 1,840 bytes on its base (136, 120, 200, 808, 576).
  The merge added 128 bytes a level: the Section 7 tracer labels
  (trace-type, trace-from) and the pre-Merge create-callee-p became three
  more keyword arguments of EXECUTE-MESSAGE-CALL-CHILD, captured by the
  stack-allocated TRACED-BODY closure, and EXECUTE-EVM-MESSAGE-CALL passed
  them.  1,024 x 1,968 = 2,015,232 bytes before the thread's own frames,
  against 2,097,152.

  Why EXECUTE-MESSAGE-CALL-CHILD was 896 bytes and alive under the child:
  it parsed eighteen keyword arguments and stack-allocated a closure over
  all of them (DYNAMIC-EXTENT TRACED-BODY) to hand to
  CALL-WITH-EVM-CALL-TRACE.  A stack-allocated closure pins its frame, so
  the call into the tracer wrapper was not a tail call even with no tracer
  bound, and all of it stayed on the stack for the life of the child.

  CREATE, same method (0x385f5f39385f5ff000: copy your own code, CREATE it
  with all the gas): 880 bytes a level at 7cef5a67 (%EXECUTE-CONTRACT-CREATION
  384, EXECUTE-CONTRACT-CREATION 240, EXECUTE-SYSTEM-OPCODE 120,
  %EXECUTE-BYTECODE-FRAME 136); unchanged by this branch.

================================================================================
3. Fix
================================================================================

(a) Smaller levels (src/runtime/evm/interpreter/call.lisp).
EXECUTE-MESSAGE-CALL-CHILD takes the opcode's EVM-MESSAGE-CALL object (which
already carried every field) plus the five values the caller computes
(precompile contract, child budget, state reservoir, create-callee-p), and
tail-calls the new %EXECUTE-MESSAGE-CALL-CHILD-FRAME when *EVM-CALL-TRACER*
is NIL, so its frame is gone before the child's is pushed.  With a tracer
bound it still stack-allocates a closure and calls CALL-WITH-EVM-CALL-TRACE
(only a tracing run pays).  The frame function reads the call's fields at
their point of use.  The two callers' WITH-SLOTS lists shrank to the slots
they read, and the unused PRECOMPILE-P binding (a known style warning) went.

  after, one CALL level = 960 bytes:
    %EXECUTE-BYTECODE-FRAME                                  136
    EXECUTE-SYSTEM-OPCODE                                    120
    EXECUTE-EVM-MESSAGE-CALL                                 152
    %EXECUTE-MESSAGE-CALL-CHILD-FRAME                        552

  1,024 levels: 983,040 bytes (0.94 MiB).  In the warm image, whose threads
  then had SBCL's 2 MiB default, the full recursion from depth 0 returned
  :STOPPED with the new call path loaded and killed nothing.

(b) An explicit stack for every executing thread.  SBCL 2.2.9's MAKE-THREAD
takes no stack size (lambda list (FUNCTION &KEY NAME ARGUMENTS); no
STACK-SIZE symbol in the image), and setting the runtime's
thread_control_stack_size from Lisp in a running image and then creating
threads ended in "Unhandled memory fault" in the eval thread (observed once,
warm image; not pursued).  The runtime option is the supported route: in a
child SBCL, --control-stack-size 8 gave thread_control_stack_size 8,388,608
and an 8 MiB control stack to the main thread and to a new thread (default:
2,097,152 each), and an executable saved with :save-runtime-options t from
such a process kept 8 MiB for both.  Set in:

  Dockerfile.runtime   the core build (sbcl --dynamic-space-size 6144
                       --control-stack-size 8 ... build-core.lisp); the
                       saved executable keeps it
  scripts/docker-test.sh, Makefile test-unit/-integration/-e2e,
  scripts/run-test-layers.sh
                       every cold and CI test runner
  tests/run-tests.lisp e2e worker processes inherit the runner's size
  scripts/dev.sh       the warm dev image

Why 8 MiB: 1,024 levels take 0.94 MiB now and at most 1.5 MiB at the
per-level ceiling the test enforces (1,536 bytes); 8 MiB holds twice that and
leaves 5 MiB for the frames beneath the EVM (block import, Engine RPC, sync,
the test harness).  The cost is address space, not memory: a thread's stack
is reserved and committed as it is touched.  Reasoning in docs/validation.md,
"The EVM depth budget", and in Dockerfile.runtime.

Tests (tests/evm-core-tests.lisp, unit):
  EVM-CALL-LEVEL-CONTROL-STACK-FITS-THE-DEPTH-BUDGET: measures bytes per
    level for CALL and CREATE as above (64 levels; 64 hook calls required as
    a positive control, every difference equal); requires each at most 1,536,
    and 2 x 1,024 x bytes within 8 MiB, within thread_control_stack_size and
    within the running thread's actual stack; requires the configured size
    to be at least 8 MiB (so a runner started without the option fails).
  EVM-SELF-CALL-AND-SELF-CREATE-REACH-THE-DEPTH-LIMIT-ON-A-FRESH-THREAD
    (replaces EVM-SELF-CALL-REACHES-THE-DEPTH-LIMIT-ON-A-DEFAULT-STACK, whose
    "default stack" is now 8 MiB): both recursions from depth 0 to the limit
    return :STOPPED on a fresh thread of the configured size.  A regression
    here kills the run rather than failing the test; the comment says so.
  EXECUTION-SBCL-LAUNCHES-CARRY-THE-EXECUTION-CONTROL-STACK: reads the
    launch lines of Dockerfile.runtime, Makefile, scripts/docker-test.sh,
    scripts/run-test-layers.sh and scripts/dev.sh that start the test
    runner, the dev image or the core build, requires --control-stack-size
    of at least 8 on each and ten such lines; positive controls: a launch
    without the option and one with 2 are both reported.
