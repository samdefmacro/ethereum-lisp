  15:06:54Z  The only line: "KV txpool record: Max fee per blob gas below blob

The node was stopped, so the head did not move between 09:10 and 15:06: the
blob transaction the restart refused was in the pool, parked, at the same head
the running process had just reconciled.

================================================================================
2. Mechanism
================================================================================

1. The running pool deliberately keeps a blob transaction whose max fee per
   blob gas is below the head's blob base fee: the fee falls again after blocks
   with little blob gas, payload building skips it while it is ineligible, and
   ENGINE-PAYLOAD-STORE-NEW-HEAD-INVALID-REASON does not remove it. Its record
   is written to the KV store with the rest of the pool.
2. On restart CHAIN-STORE-IMPORT-TXPOOL-TRANSACTION-FROM-KV
   (src/storage/node-store/persistence/import/txpool.lisp) re-ran admission
   checks against the restored head, among them
   ENGINE-PAYLOAD-STORE-VALIDATE-TXPOOL-BLOB-FEE-CAP with label "KV txpool
   record" (src/storage/txpool/service/chain-rules.lisp). Every failure was a
   BLOCK-VALIDATION-ERROR, which aborts the importer before anything is
   published, and the CLI turns that into exit 1.
3. The same shape covered two other chain-rule checks: a transaction type the
   head's fork rules do not admit (VALIDATE-TRANSACTION-TYPE-FOR-CONFIG) and a
   record whose transaction a canonical block already includes ("KV txpool
   record duplicates an indexed transaction"). Each answer can change while
   the node is stopped (a fork schedule change; a mined transaction whose
   record survived), and each turned a stale pool entry into a dead node.

Reference: go-ethereum v1.17.6 never refuses to start on its pool.
core/txpool/locals/journal.go (journal).load hands each journaled transaction
to the pool's add path, logs "Failed to add journaled transaction" at debug,
counts it as dropped and continues; TxTracker.Start ignores load's result.
core/txpool/blobpool/blobpool.go (BlobPool).Init collects every entry
parseTransaction cannot decode or recover, logs "Dropping invalidated blob
transactions", deletes them from the store and keeps starting. Neither
checks the blob fee cap against the current blob base fee: the blob pool keeps
such transactions and orders them by blob-fee jumps (blobfeeJumps,
evictionBlobFeeJumps); admission requires only the protocol minimum
(core/txpool/validation.go, BlobTxMinBlobGasprice).

================================================================================
3. Fix (9f7fe4d0)
================================================================================

The importer separates three classes.

- Restored as held: a blob transaction below the blob base fee. The import no
  longer runs the admission-time blob fee check; the record goes back into the
  blob subpool with its persisted admission time, exactly as the stopped
  process held it. This is the live failure.
- Dropped (chain rule at the restored head): the head's rules do not admit the
  type, or a canonical block includes the transaction.
  CHAIN-STORE-IMPORT-TXPOOL-TRANSACTION-DROP-REASON names the reason; the
  importer returns a drop plist (hash, subpool, reason, transaction) instead of
  signalling. NODE-STORE-IMPORT-TXPOOL-RECORDS-FROM-KV returns the drops and the
  number of records read; NODE-STORE-IMPORT-FROM-KV returns them as its second
  and third values. Once txpool change tracking is on, the drops are marked
  dirty (NODE-STORE-NOTE-DROPPED-TXPOOL-RECORDS, new
  ENGINE-PENDING-TXPOOL-MARK-DATABASE-DIRTY-TRANSACTION-HASHES), so the next
  txpool delta deletes the record and the following restart does not meet it
  again. A full snapshot export deletes it anyway.
- Still fatal (a record no process could have written): bytes that do not
  decode or round-trip, a key that is not the transaction's hash, fields no
  admission accepts, a sender that does not recover for this chain, a blob
  transaction outside the blob subpool, two records with one hash or one
  sender nonce. geth drops some of these too (blobpool Init deletes an entry
  whose sender does not recover); this change keeps them fatal on purpose,
  as the brief required: they indicate corruption, not staleness.

Logging: the CLI collects the drops during the datadir import
(*DEVNET-CLI-TXPOOL-RESTORE*, on the direct RocksDB path, the legacy file path
and the journal path) and the node logs them once it serves, beside
node.memory.budget: one txpool.restore.dropped warning per record (hash,
subpool, reason; no peer is involved) and a txpool.restore.loaded summary
(records, dropped), the counterpart of geth's "Loaded local transaction
journal". They are not written during the import, because start-up output on
stdout precedes the CLI's JSON summary (the lesson recorded for 35c4453b).

================================================================================
5. Audit of the other start-up imports
================================================================================

- Blob sidecars (import/blobs.lisp): the direct path point-reads only the
  sidecars of transactions the pool restored, so a dropped transaction's
  sidecar is never read. Fatal cases are a missing sidecar for a restored
  blob transaction (every pool snapshot writes both in one batch) and a record
  that does not decode or verify: corruption. No chain-rule check. Unchanged.
- Prepared payloads (import/prepared-payloads.lisp): legacy file path only
  (validation.md: process-private, not restart state on the direct path). A
  payload whose block is known with other bytes, or has an in-process INVALID
  verdict, is skipped silently; the fatal cases are structural. Unchanged.
- Remote blocks (import/side-data.lisp): known or verdict-owned blocks are
  skipped, age/finality pruning removes the rest; fatal only on corruption.
- INVALID verdict sweep (NODE-STORE-DISCARD-INVALID-TIPSETS-FROM-KV): deletes
  by key without decoding; nothing can be stale-fatal. Node start-up passes
  :IMPORT-INVALID-TIPSETS-P NIL on the legacy path.
- Txpool journal (DEVNET-CLI-IMPORT-TXPOOL-JOURNAL): uses the same importer,
  so the fix covers it; drops are collected and, with tracking on, marked.
- Rejournal (DEVNET-NODE-REJOURNAL): an export of the current pool, no
  re-validation; nothing stale to meet.
- Found and left alone: CHAIN-STORE-IMPORT-INVALID-TIPSETS-FROM-KV still fails
  on "KV invalid-tipset record duplicates a known block". Node start-up never
  calls it; NODE-STORE-HYDRATE-STAGED-IMPORT (the staged execution pipeline)
  does, through NODE-STORE-IMPORT-FROM-KV's default :IMPORT-INVALID-TIPSETS-P
  T, so a legacy datadir whose rejected block was later backfilled as known
  would stop a staged import.

6. Not verified
================================================================================

- No live restart of the Hoodi node on this revision; the container is still
  exited on the old binary.
- The age a transaction was admitted at is kept for records restored in their
  subpool. A record the restore moves (demotion pending -> basefee, queued ->
  pending promotion) loses it, because every subpool move in the running pool
  clears it (ENGINE-PENDING-TXPOOL-REMOVE-INDEXED-TRANSACTION); that is the
  running pool's behaviour, not new, and not changed here.
- The drop of a mined record on the direct path relies on the next head change
  carrying the dirty hash (CANONICAL-CHAIN-SET-HEAD adds every dirty txpool
  hash to the transition); the test drives the persisted transition directly.
- cold-all not run (coordinator).
