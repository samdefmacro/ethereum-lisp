=== Step 3 -- REMOTE-ONLY: Hive rpc-compat, Engine/auth, devp2p ===

Memory sequencing decision

The host has 15 GiB. The EL is bounded at 12 GiB (limit, not usage) and
Lighthouse runs beside it. Hive outer runners are bounded at: rpc-compat 2
CPU / 3 GiB (3.5 GiB with swap); Engine/auth 2 CPU / 8 GiB (10 GiB with swap;
3 GiB OOM-killed and 4 GiB produced connection-reset failures, r25-r29);
devp2p 2 CPU / 8 GiB (10 GiB with swap, r54). Earlier Hive runs shared the
host with a 7 GiB EL; with 12 GiB they cannot.

Decision:
  (a) rpc-compat runs first, WITH the EL running, only if the shadow broker's
      read-only `status` (it prints `free -b`) shows MemAvailable >= 4.5 GiB
      (3.5 GiB runner incl. swap + 1 GiB margin) and /data has >= 12 GiB free.
      Otherwise treat it like (b).
  (b) Engine/auth and devp2p cannot run beside a 12-GiB-bounded EL. They run
      back to back in one maintenance window with the EL STOPPED and
      Lighthouse left running (so the CL stays at head and EL catch-up is
      short). Expected window: Engine about 2 h 06 min (r29), devp2p about
      30 min (r54), plus staging; budget 3 h.
  (c) After the window the EL is brought back with the broker's own
      `restart`, which accepts a stopped container, re-checks revision,
      datadir and 12 GiB bounds, and prints before/after evidence. This
      restart doubles as the Section 5 restart-survival evidence at the
      accepted revision; the node must return to eth_syncing=false before
      step 4 (start-geth enforces it).
  (d) Never run Hive during the shadow window or the soak: a Hive runner
      plus geth (2 GiB) plus the EL does not fit, and a host OOM kill there
      would void the seven-day clock.
The EL stop in (b) has no broker action (finding F1). With the user's
standing authorization for this blocker the coordinator issues exactly:

=== Findings from checking the brokers against the current gate ===

F1 (live gate) There is no brokered `stop`. The Hive sequencing needs the EL
   stopped for about 3 h and `restart` accepts a stopped container, but the
   stop itself is a manual `docker stop` on the exact container. A `stop`
   action with the same ownership/revision/datadir checks as `restart` would
   close this; not added here (no shell test harness exists for the broker).
F2 (Hive) The outer runner is not brokered in this repository. r19/r29/r54
   were launched by the external Section 5 supervisor, whose runtime
   directory is absent from this control plane. Either recover that launcher
   (sha256 28d3e77c...94f4) or review a checked-in replacement before step 3;
   an ad hoc `docker run` is not the reviewed path.
F3 (shadow gate) Defaults that no longer describe the deployment: host
   test-ethereum-server (does not resolve here), source container
   hoodi-lisp-79fd759a-fresh-final / revision 79fd759a (retired). Both are
   overridable and the exports above do so. The broker also assumes a
   stopped legacy geth hoodi-geth-v1.17.4-baseline (label
   agent=codex-geth-same-host-benchmark) with a non-empty datadir
   /data/hoodi-sec5-20260814/geth-v1.17.4-baseline; no evidence file records
   that container after the 2026-09-18 disk cleanup (which removed
   geth-control-20260914), so its presence must be read from `inspect`
   before any mutation. If absent, the only reviewed way to create one is
   scripts/hoodi-geth-benchmark-gate.sh start, which takes over the
   Lighthouse alias from the Lisp EL -- a second alias cutover that has to
   be sequenced before step 4, not during it.
   Labels and topology do match the current live gate: the source check uses
   agent=codex-sec5-live-gate and io.ethereum-lisp.gate-revision, both set by
   `start`/`upgrade`; the stable alias hoodi-el-public-36a22e47 on
   hoodi-frozen and egress hoodi-net match; the proxy metric names and
   SHADOW_PROXY_* variables the broker uses all exist in tools/shadow-proxy.
   The proxy image user (shadowproxy) is overridden by --user 10001:10001,
   which passes the non-root check.
F3b (shadow memory) The shadow design text sizes the host around a 7 GiB EL.
   With the 12 GiB bound, EL limit + geth 2 GiB + proxy 128 MiB + Lighthouse
   exceeds 15 GiB; it only fits if actual EL usage stays well under its
   bound. start-geth checks MemAvailable >= 3 GiB once; nothing watches it
   during the seven days. The live gate cannot lower the bound on a running
   container (`restart` fails closed unless the limit equals the selected
   value, and `upgrade` needs a new revision), so record EL memory in every
   daily sample.
F4 (live gate `logs`) peer.snap.storage_closure is counted but none of its
   numeric fields (outcome, nodesVisited, multiGets, levels, elapsedMs) are
   projected, and peer.snap.heal_progress's localReadBatches and
   localReadWorks are missing from the projected field list. The closure
   walk's live cost (the open item from aac5f762) is therefore not readable
   through the broker; it needs a two-line addition to the field loops (no
   identity is involved) or a raw-log read. Not changed here: the brief
   allows only one-liner fixes with a test, and the broker has no test.
F4b (live gate `complete`/`logs`) Both read only the last 10,000 log lines;
   see the timing note in step 1.
F5 (hive-run.sh) devp2p has no built-in expected count, so
   HIVE_EXPECTED_TESTS=48 must be passed by hand (as step 3c does). Not
   changed: hive-run.sh is a runtime-sensitive path for the live gate, and a
   change on the gate branch would make every mutating live-gate action
   refuse for this revision.
F6 (validator soak) No validator container or index set is recorded
   anywhere in the repository; the broker has no defaults by design. Step 5
   cannot start without operator input. Its default host is also
   test-ethereum-server; the export above overrides it. Its label checks
   (io.ethereum-lisp.gate-revision on the EL container, OCI revision on its
   image) match the live gate.
