================================================================================
2. Mechanism
================================================================================

1. The rejected block's verdict lives in the in-memory invalid-tipset cache
   (keyed by its hash, plus descendant aliases). 60fb6e91 already stopped
   restoring verdicts at startup, but every INVALID answer still ran the
   durability callback with :CANDIDATE-KIND :INVALID, and the CLI adapter
   exported it (NODE-STORE-EXPORT-INVALID-CANDIDATE-TO-KV).
2. The BLOCKHASH backfill (7f079d8f, NODE-STORE-EXPORT-SNAP-HISTORY-BLOCKS-
   TO-KV) wrote the pivot's 255 ancestors as known, stateless blocks,
   3685491 among them: the CL-authorized chain contains the block we
   rejected.
3. The first tail block (3685521, a known skeleton block) was imported by
   IMPORT-P2P-BLOCK-CANDIDATE. ENGINE-PAYLOAD-STORE-INVALID-ANCESTOR walks up
   to 97 blocks through known blocks and the remote cache; 30 steps down it
   reached 3685491 and answered INVALID "links to previously rejected block".
4. The service called the durability callback with :INVALID for 3685521.
   The exporter refuses a known block (it was written to refuse persisting a
   verdict for an executed block) and signalled BLOCK-VALIDATION-ERROR. That
   is not DEVNET-PEER-SYNC-INVALID, so DEVNET-NODE-SYNC-COORDINATOR-PASS let
   it escape and the coordinator thread's outer boundary stopped the node.

Removing the refusal alone would not have been enough: the tail would then
answer DEVNET-PEER-SYNC-INVALID for every tail block on every pass (until the
128-hit eviction), because a verdict on the CL-authorized ancestry blocks the
invalid-ancestor walk. The pivot state is authenticated by the snap proofs
and the ancestry by hash from the CL target, so that verdict is our bug.

================================================================================
3. Fix
================================================================================

(i) INVALID is not durable (geth v1.17 eth/catalyst/api.go keeps
invalidTipsets and invalidBlocksHits in memory; core/blockchain.go
reportBadBlock -> rawdb.WriteBadBlock is diagnostics and never read on
import). IMPORT-P2P-BLOCK-CANDIDATE and IMPORT-EXECUTABLE-PAYLOAD run no
durability callback for INVALID; the forward batch importer's intermediate
:INVALID call is gone; the CLI adapter has no :INVALID kind;
NODE-STORE-EXPORT-INVALID-CANDIDATE-TO-KV and the full export's verdict
writer are deleted. What remains only deletes the :INVALID-TIPSET records
older revisions wrote: startup discard (60fb6e91, unchanged), the full
export's sweep (CHAIN-STORE-POPULATE-INVALID-TIPSET-DELETION-BATCH
:AUTHORITATIVE-P T), and eviction tombstones. An in-memory verdict no longer
owns BAL side data. The in-process cache and its count/byte/age/hit bounds
are unchanged. The stale buffered copy an INVALID replaces in memory leaves a
remote-block tombstone that the next durable batch deletes (before, the
:INVALID export deleted it in its own batch); after a crash in between, the
restarted node re-admits it as an ordinary candidate and re-executes it.

(ii) The backfill is coherent with process state.
DEVNET-NODE-SNAP-BACKFILL-BLOCKHASH-WINDOW, after writing (or finding) the
window, calls DEVNET-NODE-SNAP-FORGET-REJECTED-ANCESTRY: it walks the pivot
and its known ancestors down to the window's low end under the store guard,
drops each verdict with every descendant alias
(ENGINE-PAYLOAD-STORE-FORGET-INVALID-BLOCK) and logs
peer.snap.ancestry_contains_rejected_block (number, hash, pivot) per block.
Nothing is re-executed: the backfill writes no state and the tail executes
only blocks above the pivot. A verdict on a block ABOVE the pivot (a tail
block) is left alone: the tail re-imports that block and a deterministic
INVALID still ends the phase as DEVNET-PEER-SYNC-INVALID.

(iii) "Snap pivot state import returned before completion" (STORAGE-FAIL)
is DEVNET-SNAP-STATE-INCOMPLETE, contained by the coordinator pass as
peer.snap.state_incomplete; the next pass resumes from the durable cursors.

6. Not verified
================================================================================

- Live: nothing deployed. The next Hoodi run that meets a rejected block
  inside a rebased pivot's window should log
  peer.snap.ancestry_contains_rejected_block and complete the target.
- The Engine newPayload path of C1 (a known block whose ancestor carries a
  verdict) is removed with the export but was not reproduced separately.
- C3 is reproduced with an importer double; in production
  SNAP-SYNC-IMPORT-STATE-MULTI returns an incomplete progress only through
  its MAX-PAGES limit (:LIMITED), which the CLI never sets. The conversion
  removes a latent exit, not an observed one.
- O1: "Snap workers stopped without source-failure evidence" is a plain
  ERROR that would stop the node; the range workers' claim/fail bookkeeping
  makes it unreachable today (a worker leaves only by stop, completion or a
  reported failure). Not converted.
- O2: a DEVNET-PEER-SYNC-INVALID raised by gap fill on a peer's request
  queue ends that peer's session (peer.dial.failed with the verdict text,
  1a7b9059 log 07:14:25Z-07:14:34Z): a verdict about a block is charged to
  the transport that delivered it. Not an exit; not changed here.
- The legacy importers (NODE-STORE-IMPORT-FROM-KV :IMPORT-INVALID-TIPSETS-P,
  default T; NODE-STORE-IMPORT-BOUNDED-INVALID-TIPSETS-FROM-KV) still read
  :invalid-tipset records if a caller asks; the node's startup paths pass
  NIL / discard. Nothing writes such records any more.
- EEST was not rerun: no execution, root, receipt or gas code changed.
