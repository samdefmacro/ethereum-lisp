2. The Lisp side: dynamic-space RSS follows the heap
================================================================================

At 02:19 the dynamic space held 3,767 MiB resident against heapMb 3.3-3.5 GB,
so the gap between Lisp RSS and the Lisp heap is ~0.3-0.5 GB (the nursery and
garbage not yet collected), not gigabytes.  Measured in the dev image (SBCL
2.2.9, arm64): 300 MB of live byte vectors, dropped, then collected:

  retained           heap 391 MB  RssAnon 401 MB
  nursery GC only    heap 391 MB  RssAnon 401 MB   (objects already promoted)
  full GC            heap  99 MB  RssAnon  83 MB   (free pages returned)

and, with 243 MB promoted to generation 2 before it was dropped:

  gc :gen 0          heap 344 MB  RssAnon 389 MB
  gc :gen 1          heap 344 MB  RssAnon 389 MB
  gc :gen 2          heap 101 MB  RssAnon 124 MB   (= the baseline)

So SBCL 2.2.9 returns the pages when the collection that frees them runs, an
ordinary generational one included, and the snap-phase high-water mark of the
Lisp heap does come back.  No post-sync full GC is added: it would buy
nothing the ordinary generational collections do not already return, and
34b7ff97 removed in-phase full GCs because one outlasted the CL's 5-second
Engine upcheck.  The 6 GiB dynamic space stays: the heap reached 3.95 GB, so a
smaller space would have ended the process with heap exhaustion instead.

================================================================================
3. The native side: mechanism, reproduction, fix
================================================================================

Mechanism.  glibc serves a request of at least M_MMAP_THRESHOLD with its own
mmap, returned to the kernel on free.  The threshold starts at 128 KiB and is
dynamic: freeing an mmapped block raises it to that block's size (up to
32 MiB).  One freed batch buffer or memtable is enough; from then on every
1 MiB memtable arena block, write-batch string and compaction buffer below the
new threshold comes from a malloc arena.  Freed arena memory stays resident
unless it is at the top of its heap, and a thread that contends gets its own
arena (up to 8 per core), so ~100 node and RocksDB threads multiply it.

Reproduction 1, RocksDB churn (child SBCL per configuration, dev image,
32 writer threads x 40 batches x 3,000 keys of 32-732 bytes, a 64-key
multi-get after each batch; ~110 MiB live at the end):

  configuration          C-side resident MiB       malloc      trim
                         after churn  after trim   heaps       ms
  glibc default (dynamic)     407         156        47         17
  M_ARENA_MAX 4               336         100         4         15
  mmap threshold 128 KiB      104         100        47          1
  mmap threshold 1 MiB        109         105        47          0
  arena 4 + threshold 1 MiB   100          96         4          1

  (C-side resident = RssAnon less the dynamic space's anonymous resident
  pages.  malloc in use ~110 MiB in every configuration; with the threshold
  pinned ~80-100 MiB of it is mmapped memtable memory.)

Reproduction 2, the mechanism in isolation (test NATIVE-MALLOC-PINNED-MMAP-
THRESHOLD-RETURNS-FREED-MEGABYTE-BLOCKS, a child SBCL per arm): free one
4 MiB block (raises the threshold), then on a thread allocate 64 x 1 MiB
blocks each followed by a live 64-byte pin, touch and free them:
  dynamic threshold   66,125,824 bytes still resident (of 67,108,864)
  pinned at 128 KiB    2,113,536 bytes still resident

Reproduction 3, the release (test NATIVE-MALLOC-RELEASE-RETURNS-FREED-ARENA-
PAGES): 1,024 x 64 KiB pinned blocks freed on a thread: 60 of 64 MiB still
resident after free; malloc_trim(0) returned 60 MiB in 4-5 ms (3 runs).

Fix (a910eeea).
  - NATIVE-MALLOC-CONFIGURE pins M_MMAP_THRESHOLD at 128 KiB (glibc's own
    initial value; pinning also switches off the dynamic climb) at CLI
    start-up, before any database opens.  128 KiB rather than 1 MiB because
    it changes nothing but the climb; both measured the same.
  - A memory-maintenance worker (joined like every other worker) calls
    malloc_trim(0) every 60 s, and logs node.memory.sample every 300 s.
  - peer.snap.target_completed is followed by a release
    (node.memory.release reason snap-target-completed).  This is a CLI hook
    after the phase; no snap-sync client logic changed.
  - --memory.budget MIB (default 7168, the Hoodi gate's 7 GiB) derives the
    RocksDB block cache (1/28) and the level-compaction write-buffer budget
    (3/56; memtables at most 3/2 of it).  7 GiB -> 256 MiB + 384 MiB (576 MiB
    memtables), i.e. the values Hoodi runs were tuned with; 12 GiB -> 438 +
    658 MiB.  max_open_files stays -1 (index and filter blocks are charged to
    the block cache).  WAL, sync writes and wal_bytes_per_sync unchanged.
  - M_ARENA_MAX is NOT capped: with the threshold pinned it bought 4-9 MiB
    here, and fewer arenas would add allocator lock contention across ~100
    threads that nothing here measured.

Budget arithmetic for a 7 GiB container (logged when the node serves as
node.memory.budget): RocksDB 832 MiB bounded (256 + 576), dynamic space up to
6,144 MiB, headroom 192 MiB; thread stacks and libraries ~130 MiB, file cache
is charged to the cgroup too but is reclaimable.  So 7 GiB holds the node only
while the live Lisp heap stays near or below ~5.5 GiB.  It did until 01:50 on
this run (max 2.6-2.9 GB); after 01:50 it did not stop growing.

Devnet import measurement (child SBCL per mode, 4 GiB dynamic space: 120
blocks of 32 transfers over 10,000 funded accounts built on a memory node,
then imported through newPayload + forkchoiceUpdated into a fresh RocksDB
devnet node, one worker thread per block; the harness reuses the
DEVNET-NEW-PAYLOAD-READS fixture builders):

  mode      rssAnon  lispResident  nativeResident  malloc in use  heaps
  dynamic    108 MiB      91 MiB          17 MiB          14 MiB     13
  pinned     112 MiB      91 MiB          21 MiB          14 MiB     13
    after release (0 ms)  95 MiB          21 MiB

At this size the import takes 3 s and writes a few MiB: it never fills a
memtable, so it cannot exercise the caches, and both modes end at the same
C-side footprint (the pinned run is no worse).  Reaching RocksDB churn
through Engine imports would need hours of blocks; the churn benchmark above
drives the same RocksDB adapter directly instead.  (A 300-block, 20,000-
account attempt exhausted the 3 GiB builder heap and was abandoned.)
