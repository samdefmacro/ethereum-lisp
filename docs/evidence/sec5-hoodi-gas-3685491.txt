Section 5: the gas-used mismatch on Hoodi block 3685491 (3 gas short)

Status

Branch hoodi-gas-3685491, from 1a7b9059. Found, reproduced to the unit,
fixed. Not deployed.

  Live (R6 = 1a7b9059, 2026-09-24T06:53:37Z, Lighthouse on the Hoodi host),
  after the node had reached head and returned 44 VALID newPayloads:
    "Gas used mismatch at block 3685491: header=58730304 computed=58730301"
    block 0x154fcffe66c2595543e1f7f07b5504815709a971c0619e3c5c8dfbcab404c2f7
  Every later block answered "links to previously rejected block".

It is NOT the interpreter throughput work (5fee5219), NOT the base-gas table
(43be69c5) and NOT the lazy state (72d148aa). It is a memory-sizing rule that
predates all three: LOG, KECCAK256, CREATE and CREATE2 charged nothing for an
EMPTY memory region (correct) but still grew memory to the region's offset
(wrong). The next real expansion in the frame was then priced from the larger
size. go-ethereum never resizes memory for a zero-length region.

Revision

  d7a28c6c  evm: a zero-length LOG, KECCAK256, CREATE or CREATE2 grows no memory
  3c58f4a5  test: Hoodi block 3685491's gas matches its header on a backed state
  (the commit adding this record follows them)

2. Which instruction
================================================================================

go-ethereum's callTracer for transaction 7 against our own call tracer
(*EVM-CALL-TRACER*, a synthetic root frame entered first so the top-level
calls stay children): the first frame whose gasUsed differs by 3 is the
DELEGATECALL from the CREATE2 initcode of the new account 0x39a8736a into its
implementation 0x8abb1336 (input 0xc4d66de8 = initialize(address), gas
597,895): geth 26,114, ours 26,111. Every frame before it matched.

go-ethereum's struct log of that frame (default struct logger, storage and
memory off, 213 steps at depth 5) against our own steps (a temporary hook in
STEP-EVM-MACHINE recording pc, opcode and regular gas left; removed before any
commit): pcs and gas agree for 196 steps; step 197 is

  pc 3871  MSTORE  offset 0x80   gas before 572,839   geth cost 9   ours 6

Memory in that frame, in go-ethereum:
  pc 4     MSTORE 0x40 (free-memory pointer)   -> 3 words, cost 3 + 9
  pc 5691  LOG3 offset 0x80 size 0             -> no resize, cost 1,500
           (topic 0x47e55c76..., then the EntryPoint and owner addresses as
           indexed topics; no data)
  pc 3871  MSTORE 0x80                          -> 3 to 5 words, cost 3 + 6
Ours: the LOG3 grew memory to 0x80 (4 words) without charging, so the MSTORE
paid 4 to 5 words, 3 + 3. The 3 gas is one word of memory expansion
(G_memory), not a VERYLOW instruction.

================================================================================
3. Mechanism and reference
================================================================================

The LOG handler (src/runtime/evm/opcodes/stack-log.lisp) charged
MEMORY-EXPANSION-GAS, which is 0 for a zero size, then called
(ENSURE-MEMORY-SIZE memory (+ offset size)) unconditionally. The same shape was
in KECCAK256 (opcodes/arithmetic.lisp), CREATE and CREATE2
(opcodes/system.lisp). git blame puts the LOG form in 94a0ade3 (the vector
stack) only as a moved line: the list-stack code before it had the identical
unconditional resize, so the defect predates the throughput work.

go-ethereum v1.17.6 (the local reference tree):
  core/vm/common.go calcMemSize64WithUint: "if length is zero, memsize is
    always zero, regardless of offset"
  core/vm/memory_table.go memoryLog / memoryKeccak256 / memoryCreate /
    memoryCreate2 all go through calcMemSize64
  core/vm/interpreter.go: "if memorySize > 0 { mem.Resize(memorySize) }"

The other memory users already skipped empty regions: RETURN and REVERT
(MEMORY-SLICE), the copy opcodes (COPY-INTO-MEMORY), MCOPY
(COPY-MEMORY-REGION) and the CALL family (MEMORY-REGIONS-HIGH-WATER). The
audit covered every ENSURE-MEMORY-SIZE, MEMORY-SLICE, COPY-INTO-MEMORY and
COPY-MEMORY-REGION caller under src/.

Consequences before the fix:
  - an empty LOG/KECCAK256/CREATE/CREATE2 at an offset past the current memory
    made MSIZE read too high and under-priced the next expansion in the frame
    by the gap (here one word, 3 gas);
  - with a huge offset (the unit test uses 2^256 - 1) and size 0, which geth
    accepts at no memory cost, the resize signalled a Lisp TYPE-ERROR (the
    aligned size 2^256 is not an array dimension) instead of executing.

EEST v20.0.2 passed 8/8 both with the defect (591f700e, cbfe2c63, 70409b12)
and without it (section 7), so no selected vector observes the difference;
the corpus was not searched for the pattern. The 44 blocks accepted before
3685491 evidently did not combine a data-less event past the end of memory
with a later expansion in the same frame (inferred from their acceptance, not
traced).

================================================================================
4. Fix
================================================================================

d7a28c6c. ENSURE-MEMORY-REGION (src/runtime/evm/memory.lisp) returns MEMORY
unchanged for a zero SIZE and otherwise calls ENSURE-MEMORY-SIZE with
OFFSET + SIZE; LOG0-LOG4, KECCAK256, CREATE and CREATE2 call it. Gas charging
is unchanged (it was already zero for an empty region).

6. Rebuilding the fixture
================================================================================

The fixture (about 0.3 MB) is fetched, not committed; the directory matches
/.eest-fixtures*/ in .gitignore. From the checkout root, with the block
saved as block-3685491.json (eth_getBlockByNumber "0x383c73" true on
ethereum-hoodi-rpc.publicnode.com), control plane only (curl, jq):

  B=$PWD/block-3685491.json
  mkdir -p .eest-fixtures-hoodi-3685491 && cd .eest-fixtures-hoodi-3685491
  : > transactions.txt
  for h in $(jq -r '.result.transactions[].hash' $B); do
    curl -s -X POST -H 'content-type: application/json' --data \
      "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"debug_traceTransaction\",\"params\":[\"$h\",{\"tracer\":\"prestateTracer\"}]}" \
      https://rpc.hoodi.ethpandaops.io > pre-$h.json
    curl -s -X POST -H 'content-type: application/json' --data \
      "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"eth_getRawTransactionByHash\",\"params\":[\"$h\"]}" \
      https://ethereum-hoodi-rpc.publicnode.com | jq -r .result >> transactions.txt
  done
  jq -s 'reduce (.[] | .result) as $p ({}; reduce ($p|to_entries[]) as $e (.;
    if has($e.key) then .[$e.key].storage = (($e.value.storage // {}) + (.[$e.key].storage // {}))
    else .[$e.key] = $e.value end))' \
    $(for h in $(jq -r '.result.transactions[].hash' $B); do echo pre-$h.json; done) \
    > prestate.json

Expected: 36 lines in transactions.txt, 68 accounts in prestate.json. The
test reads only prestate.json and transactions.txt.

================================================================================
8. Operational note
================================================================================

The R6 datadir needs no store operation: since 60fb6e91 INVALID verdicts are
not restored at startup, so a runtime built with d7a28c6c re-executes block
3685491 on its next newPayload (expected VALID, gasUsed 58,730,304). A
runtime without d7a28c6c rejects it again. State written before the rejection
is sound: each earlier block matched its header's state root, receipts root
and gasUsed.
