Section 5: post-order sentinels and the healer's local read width

Status

The sentinel mechanism is fixed and measured: a local read batch now keeps
popping past a post-order sentinel instead of closing on it, and a sentinel
still runs only after every node it waits for. Measured in an arm64 warm image
on memory and RocksDB stores, not on the Hoodi host. No live run.

The brief's diagnosis of the live width was NOT confirmed. The Hoodi width
of exactly one on 75b0b7a7 is not the sentinel rule. It is the checkpoint-room
term of the read limit, which saturates at one once 262,144 nodes have been
processed without a checkpoint, while no checkpoint can be written above 8,192
frontier works. At the coordinator's request that term is fixed here too
(3e7cbd65): checkpoint room no longer binds a frontier that cannot be
checkpointed. The sentinel change alone does not move the live width; the
checkpoint-room change is the one aimed at it.

What the sentinel rule did

src/networking/snap-sync/client.lisp, COLLECT-MISSING and the main loop's
copy of the same batch loop. A marked node, when integrated, pushes its
:NODE-COMPLETE sentinel and then its children above it (an :ARMED node also
pushes a :COMPLETE sentinel for its healed-subtree record). Popping a sentinel
did, in order:

  missing work in this pass, or remote work        -> block it (unchanged)
  the batch already holds a lookup, or storage is  -> push it back and close
  deferred                                            the batch
  otherwise                                         -> run it

So over a subtree in which every node is marked, a batch is the children of
one node, then that node's sentinel closes it: the mean width is the mean
fan-out. On the fixture below that is 3.58; across the fixture shapes tried it
was 2.5 to 4.0 (1,000 accounts x 2 slots: 2.55; 1 account x 3,000 slots:
3.95). It is never below 2 on a real trie, so the brief's RED threshold
("below 2 on 75b0b7a7") does not hold for this mechanism; the control arm
below asserts below 4 instead.

The change

When a sentinel is popped and the batch already holds a lookup, the batch
CARRIES it (off the stack, still counted in the frontier) and keeps popping.
After the batch is integrated, SNAP-SYNC-HEAL-RESTORE-CARRIED-COMPLETIONS puts
the carried sentinels back, in their original order, on the stack as it stood
when popping stopped -- i.e. BELOW every work integration pushed.

Why no sentinel runs early: a sentinel's trie descendants were all above it
when the batch reached it, so the batch popped every one of them. After
integration each is resolved, or its children are above the sentinel again,
or it is missing, and a pass with missing work blocks every sentinel it
reaches (that rule is decided first and is unchanged). Account-leaf storage
roots go to the deferred list and reach the stack only on top of it (the
sentinel-time drain and the end-of-pass drain), and a sentinel popped with
storage deferred still drains instead of running. A carried sentinel is never
run in the batch that carried it.

This is option 2 of the brief. It keeps sentinels on the stack between
batches, so the checkpoint format is untouched and a resumed heal restores
sentinels exactly as before; option 1 (dependency counters) would have needed
a new durable frontier encoding.

The bound that matters. An unbounded carry turns the depth-first walk into a
slice across sibling subtrees, and the frontier grows with it: on a
33,232-node fixture an unbounded carry reached a peak frontier of 11,910
works, past the 8,192 a checkpoint can record. Once a checkpoint falls due,
such a frontier holds every later read at width one until it drains (the
live finding below). So a batch carries only while

  stack + deferred + 63 x (lookups + 1)  <=  8,192

i.e. while its worst-case expansion (the limiter's own 63-per-work figure)
still fits one durable checkpoint. Above that the walk closes at sentinels and
stays depth first, exactly as before. Variants measured on the same 33,232-node
fixture (mean width / peak frontier):

  no carry (previous rule)                    3.71 /    362
  carry, unbounded                          377.6  / 11,910
  carry while stack + lookups <= 4,096        4.30 /  7,563
  carry while worst case fits 8,192          66.2  /  5,763   <- shipped

A per-batch carry count bound, *SNAP-SYNC-HEAL-CARRIED-COMPLETIONS-PER-BATCH*
(4,096), keeps one batch from carrying a long run of restored blocked
sentinels back and forth; zero is the previous rule and is how the test's
control arm runs.

Nothing else changes: which nodes are walked, the skip decision, the epoch,
SNAP-SYNC-HEAL-LOCAL-READ-LIMIT, the frontier bounds and the checkpoint
format.

The live width of one: the checkpoint-room term (fixed in 3e7cbd65)

SNAP-SYNC-HEAL-LOCAL-READ-LIMIT takes CHECKPOINT-ROOM, computed in both batch
loops as

  max(1, 262,144 - (processed-nodes - last-checkpoint-processed-nodes))

LAST-CHECKPOINT-PROCESSED-NODES moves only in PERSIST-CHECKPOINT, and a
checkpoint is written only when the frontier is at most 8,192 works
(SNAP-SYNC-HEAL-CHECKPOINT-FRONTIER-P); CHECKPOINT-BLOCKS-TRAVERSAL-P stops the
walk to drain only when the frontier is already at most 8,192. A heal whose
frontier stays above 8,192 therefore never checkpoints, and after 262,144
processed nodes every batch is exactly one work, whatever the sentinels do.

Hoodi on 75b0b7a7: healing from about 21:20Z, width 22 at the start (frontier
127k), processedNodes 354,304 at 21:47Z with frontierWorks 451,583, and
afterwards localReadBatches = localReadWorks per window (width exactly 1).
The frontier is mostly restored blocked sentinels at the bottom of the stack,
which cannot run until everything above them has, so it cannot drain below
8,192 before the heal ends: width one is permanent for the rest of the run.

The fix. SNAP-SYNC-HEAL-LOCAL-READ-LIMIT lets CHECKPOINT-ROOM bind only while
the frontier it is given is at or below +SNAP-SYNC-HEAL-CHECKPOINT-MAX-WORKS+
(8,192). Both batch loops compute the room the same way and pass it to this
one function, so the one change covers both. Inside the checkpoint region the
rule is unchanged, so a frontier that is at or below 8,192 when a checkpoint
falls due still stops at the room and checkpoints on the usual 262,144-node
schedule. Nothing else in the limiter, the checkpoint rule or the frontier
bounds changes.

What a frontier that never drains below 8,192 means for checkpointing

The heal checkpoint rule is unchanged and is recorded here, not fixed. A
checkpoint records the whole frontier in one record of at most 8,192 works.
Hoodi's frontier passed 127k works at the start of healing and grew to 451k,
mostly blocked post-order sentinels restored to the bottom of the stack, which
cannot run before everything above them. It therefore never returns to 8,192
before the walk ends, and on that run NO heal checkpoint is ever written. A
restart mid-heal resumes from the older checkpoint or, having none, from the
authorized root, and re-walks what it had already walked; a pivot rebase
deletes the heal checkpoint anyway (SNAP-SYNC-POPULATE-REBASED-PROGRESS-BATCH)
and re-seeds the walk from the new root, which on Hoodi happens about every
30 minutes. Content-addressed nodes and deleted markers survive either way;
only the in-memory frontier is lost.

The parent rule did not change that outcome: its width-one reads were meant
to drain a frontier into the checkpoint region, and on Hoodi they could not.
With the fix, a frontier above 8,192 is no longer pushed down by width-one
reads once a checkpoint falls due. A frontier that was only transiently above
8,192 (a resumed or refilled one, say) now reaches a checkpoint only when the
walk itself brings it back into the region, not by being drained; that is the
trade this change makes, and it is not measured here beyond the fixtures above.
