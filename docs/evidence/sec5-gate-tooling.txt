================================================================================
1. live-gate logs: the Engine and store-guard summary
================================================================================

Mechanism. The node writes engine.rpc.http.request with bare integer fields
(("handlerMs" . 25269)) and node.store_guard.long_hold with string fields
(("holdMs" . "5996")); neither carries a time. The EL window (last 10,000
lines, as before) is now read with `docker logs --timestamps`; the stamps are
stripped into the copy every existing reader uses, so their patterns (the
anchored allocation-profile-row pass-through included) see the node's lines
unchanged. One awk pass over the stamped copy accepts both field spellings
and prints, sorted for stable output:

  el-engine-requests method=M count=N           per rpcMethods, and -total
  el-engine-latency series=handlerMs|npExecuteMs method=M
                    samples= min= p50= p90= max=   nearest rank
  el-engine-np-cpu-gc samples= npExecuteCpuMs-sum= npExecuteGcMs-sum=
  el-engine-guard-wait samples= maxMs=           guardWaitMs
  el-engine-last-new-payload timestamp= method= status=
                                              (none-in-window when older)
  el-guard-long-hold holder=H count= maxMs=      and -total, -last
  el-connection-error port=P class=C count=      and -total

"Per method deadline" for connection errors: the event carries only the
listener fields and the error text, and a request that reaches its deadline
writes no engine.rpc.http.request line (all 1,245 request lines in the
b5161312 window had status 200). So the method is not observable from the
log; the class is: request-deadline-Ns and idle-deadline-Ns come from the two
fixed messages in src/transport/http/parser.lisp, everything else is other.
Only numbers, method names, holder labels and the class leave the host;
guardWaitedFor lists and error text never do.

Live read (read-only, b5161312, 2026-09-24T02:1x Z, before the OOM kill in
section 6), last 10,000 lines:

2. live-gate complete: why the node is not at the head
================================================================================

When eth_syncing is not false, complete still exits 1 and prints one
completion-why line. A hold is logged only at release, so an open hold is
not observable without a new event (src/ was out of scope). The line
reports the last observable release instead (latest long_hold, newPayload or
forkchoiceUpdated line, each of which took and released the guard) and says
no-release-logged-since:<ts> once that is >= 30 s old (the Engine request
deadline). complete now reads the whole log with --timestamps; all of its
patterns are unanchored.

3. hive-gate upload from an exported archive
================================================================================

HOODI_HIVE_IMAGE_TAR=PATH with HOODI_HIVE_IMAGE_SHA256=HEX replaces the
local-daemon identity check: the archive's SHA-256 must equal the pin
(prepare checks it again), and its single image's RepoTags must include
ethereum-lisp-runtime:sec5-<rev8>-amd64, its configuration must carry
exactly one org.opencontainers.image.revision label equal to the revision,
and os/architecture must be linux/amd64, read with tar, grep and sed (the
test image has no jq). The revision fence runs first and is unchanged; the
nested runner still checks revision, platform and user at load time.
