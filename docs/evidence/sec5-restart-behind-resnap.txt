================================================================================
1. Why the node re-entered SNAP
================================================================================

(a) The finished session read as unfinished. DEVNET-NODE-DURABLE-SNAP-PIVOT-
NUMBER and DEVNET-NODE-ACTIVE-SNAP-TARGET treated a completed session as
residue only while its target's own state was available. The state retention
window (+chain-store-default-state-retention-depth+ = 128;
node-store-populate-state-retention-batch deletes :state-history records
behind the head) had deleted it while the node followed the head, so after
the restart the old target (pivot 3680535) was pinned again: exactly the
fromPivot in the live log.

(b) Any target more than +devnet-snap-pivot-distance+ (64) ahead went to SNAP,
even from a synced head with executable state. geth 38271784
eth/downloader/syncmode.go: newSyncModer/get switch to full sync once the head
(number > 0) has state, and re-enable snap only when head < last pivot or the
head state is missing -- no distance bound at all. Nethermind e52dc19a
SyncConfig.cs FastSyncCatchUpHeightDelta default 8192 is the documented bound
this client adopts.

================================================================================
2. Why it died
================================================================================

IMPORT-P2P-BLOCK-CANDIDATE checked (null parent) before any known-block
branch, so a block the SNAP skeleton had already made known, arriving again
with its parent missing, was put in the remote cache and handed to the
durable adapter as :buffered; NODE-STORE-EXPORT-BUFFERED-CANDIDATE-TO-KV
refuses a known block (its invariant) and the block-validation-error escaped
the coordinator's handled classes. The Engine path already returned no
candidate for a known block with a missing parent, and wraps adapter errors
as "New payload persistence failed: ...", so the bare live message points at
the P2P import path. The same known-block buffering existed in both
state-unavailable handlers (P2P and Engine).

================================================================================
3. Fix (commit 6b37b097)
================================================================================

- DEVNET-STORE-SNAP-TARGET-PASSED-P: a session target has passed when its
  state is available, or it is canonical under a head with executable state
  (a canonical target executed: the pivot tail runs before any forkchoice
  publishes it). Used by DURABLE-SNAP-PIVOT-NUMBER and ACTIVE-SNAP-TARGET. An
  unfinished session (completed-p false) still pins SNAP.
- +DEVNET-FORWARD-SYNC-MAXIMUM-DISTANCE+ = 8192 and
  DEVNET-STORE-FORWARD-SYNC-ELIGIBLE-P (head > 0, head state available,
  distance <= bound). SNAP-TARGET-REQUIRED-P sends a >64 gap to SNAP only when
  not eligible; DEVNET-NODE-FORWARD-SYNC-TARGET-P routes a CL-buffered target
  of such a gap to the multi-peer forward batch downloader (number-range from
  head+1, DEVNET-PEER-SYNC-IMPORT-BATCH) instead of the hash gap fill; the
  forward path's "wait for FCU" guard applies only when not eligible. Fresh
  node (head 0), head without state, unfinished durable session, unknown
  target, or gap > 8192: SNAP as before.
- Known blocks are never buffered: P2P (known, parent missing) and both
  state-unavailable handlers answer SYNCING with no candidate; the devnet
  :buffered persistence adapter skips a known block. The exporter's refusal
  itself is unchanged (still asserted by
  node-store-buffered-candidate-export-is-atomic-and-cache-bound).
