1. Where a peer is scored or its session ends (a6d2b58b), against geth v1.17.6
================================================================================

Scores live in the peer table (DEVNET-PEER-NOTE-SCORE). They never decay; at
+DEVNET-PEER-BAN-SCORE+ (-100) DEVNET-PEER-TABLE-INBOUND-VERDICT answers
:USELESS-PEER for that id, inbound and outbound, for the life of the process.
geth v1.17.6 keeps no peer score at all.

geth v1.17.6, cited by function:

- eth/downloader/downloader.go importBlockResults (lines 893-913): when
  InsertChain fails, it calls the badBlock callback (the Engine API's
  invalid-tipset cache) and returns errInvalidChain, which aborts the sync
  cycle. No peer is dropped. On delivery, fetchers_concurrent.go line 342
  hands the delivering peer's handler only validityErrorOfRequest(err)
  (lines 364-369), non-nil only for errInvalidBody / errInvalidReceipt: a
  body or receipt list that does not match its header (queue.go
  DeliverBodies / DeliverReceipts, lines 561-633). That error returned to the
  eth handler disconnects the peer.
- eth/downloader/beaconsync.go beaconBackfiller.resume (lines 107-110): a
  failed backfill cycle is logged, nothing else.
- The downloader drops (handler.go removePeer, lines 425-431:
  Disconnect(DiscUselessPeer)) only a peer that stalls a request past the
  grace period (fetchers_concurrent.go line 151) or times out while it has not
  yet failed three times (line 301). The skeleton drops a peer whose header
  request times out (skeleton.go line 862) or whose headers do not link to
  the subchain (line 1063).
- eth/protocols/snap/sync.go: a timed-out request records a zero delivery and
  is reverted (lines 1088, 1199, 1347, 1484), the peer stays; an empty answer
  marks the peer stateless for this sync (2574, 2684, 2812, 2931, 3038); only
  a proof that fails verification is returned as an error (2593-2597), which
  the snap handler returns and the peer is disconnected. With no idle peer the
  assignment loop simply assigns nothing; no one is charged.
- p2p/peer_error.go discReasonForError (lines 105-122): an unwrapped
  *peerError errInvalidMsg (what msg.Decode returns, p2p/message.go:57) is
  DiscProtocolError (2); any other protocol error is DiscSubprotocolError (16).

Divergences from geth, and what this branch does with them:

 D1 T1: an INVALID verdict from the gap fill job ended the peer's session and
    (S1) cost it 25. geth never disconnects for an execution failure.  FIXED.
 D2 S1: a session ending on a remote Disconnect, a reset or broken pipe, a
    timeout or a local fault cost the peer 25, four of them a ban. geth keeps
    no score.                                                          FIXED.
 D3 S4: "no live SNAP peer can serve ~A" (a SIMPLE-ERROR from
    DEVNET-SNAP-SOURCE-POOL-CALL) was charged -50 to the account-page peer,
    and so was the last failing dependency transport's own condition when it
    was re-signalled after that transport left the pool.               FIXED.
 D4 "Snap workers stopped without source-failure evidence" was a plain
    ERROR; had it happened, the coordinator's outer boundary would have
    stopped the node.                                                  FIXED.
 D5 T6 and T5 are more lenient than geth: a body whose commitments do not
    match its header, or a dependency proof that fails, keeps the session
    (geth disconnects). Not changed; reported.
 D6 T3: when the multi-peer downloader aborts (an INVALID verdict included)
    it closes the stream of every source with a request in flight, ending
    those sessions; geth cancels the requests and keeps the peers. Not
    changed: not observed in the 1a7b9059 log (one peer.sync.multi_completed,
    no peer.sync.source_penalty); reported.
 D7 S2 :failed charges -25 for any failed fetch, transport losses included.
    Same shape as D2 but on the downloader's own penalty; not observed in the
    1a7b9059 log. Not changed; reported.

3. Fix (5e6240fc)
================================================================================

src/app/cli/devnet/peer-manager.lisp
  DEVNET-PEER-PENDING-REQUEST: a job's condition is still handed to its
  submitter, and still ends the session, unless DEVNET-PEER-REQUEST-VERDICT-P:
  a DEVNET-PEER-SYNC-INVALID (a deterministic INVALID from executing a block
  the peer delivered). D1.
  DEVNET-PEER-RUN-SESSION charges -25 only when
  DEVNET-PEER-SESSION-END-CHARGES-PEER-P: not for RLPX-DISCONNECT,
  STREAM-ERROR, SOCKET-ERROR, TIMEOUT, STORAGE-ERROR or a closed request
  queue, including those wrapped in ETH-SYNC-PEER-TRANSPORT-ERROR. A peer
  message we could not accept is still charged: decoder failures are plain
  ERRORs and cannot be told apart from a local program error, so both stay
  charged. D2.
src/app/cli/devnet/dialer.lisp
  DEVNET-SNAP-SOURCE-POOL-EXHAUSTED (label, last failure) replaces the
  SIMPLE-ERROR and the re-signalled last transport condition; a request
  timeout is still re-signalled, so the range worker retries without retiring
  its source. S4 logs it as peer.snap.dependencies_exhausted and scores
  nobody. D3.
  The coordinator pass contains SNAP-SYNC-WORKERS-STOPPED as
  peer.snap.workers_stopped. D4.
src/networking/snap-sync/client.lisp, src/packages/runtime.lisp
  SNAP-SYNC-WORKERS-STOPPED, a SNAP-SYNC-SOURCES-EXHAUSTED with no failures,
  exported; SNAP-SYNC-SIGNAL-SOURCES-EXHAUSTED signals it for an empty list.
scripts/hoodi-live-gate.sh counts the two new events.
docs/evidence/sec5-eth72-interop.txt: geth's reason for a decode failure is
DiscProtocolError (2), not DiscSubprotocolError.
