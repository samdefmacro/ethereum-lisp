Parent 911a56ef, branch sec5-public-bootstrap-sync. Subject file

Change

Three consumers of the deferred-storage plan no longer depend on the plan's
width. SNAP-SYNC-PROMOTE-COMPLETE-RANGE-PLAN, SNAP-SYNC-RANGE-PLAN-FULLY-
DURABLE-P and SNAP-SYNC-FILL-DEFERRED-STORAGE all loaded the plan through
SNAP-SYNC-DEFERRED-STORAGE-WORKS and fail-closed above
*SNAP-SYNC-DEFERRED-STORAGE-MAX-WORKS* (8,192). They now walk the whole plan
through the new SNAP-SYNC-MAP-DEFERRED-STORAGE-PLAN, which loads consecutive
segments from SNAP-SYNC-DEFERRED-STORAGE-SEGMENT and its exclusive cursor.

  - promotion retains only the set of unsafe account prefix buckets, bounded by
    the bucket space (65,536 at depth four, 1,048,576 at depth five) rather than
    by the plan width, then promotes exactly as before;
  - durability is a short-circuiting stream: NIL at the first non-durable root,
    T only after the plan is exhausted;
  - the StorageRanges second pass streams sequentially, stopping at the first
    root it cannot finish, which is what its previous DOLIST did.

SNAP-SYNC-DEFERRED-STORAGE-WORKS is retired. No caller remained, and it
disagreed with SNAP-SYNC-DEFERRED-STORAGE-SEGMENT on the boundary: it pushed
first and flagged overflow at 8,193 works, while the segment loader caps at
exactly 8,192 and reports the remainder. The segment loader is now the only
place the bound is applied, which is where the boundary inconsistency is
reconciled.

SNAP-SYNC-RETIRE-LEGACY-STORAGE-ROOT-PROOF becomes
SNAP-SYNC-POPULATE-LEGACY-STORAGE-ROOT-RETIREMENT-BATCH: it populates a caller
batch instead of applying one per work, and promotion flushes at
+SNAP-SYNC-HEALED-SUBTREES-PER-BATCH+ and again before the first promoted proof.

Why

The bound was never a safety property of these consumers; it was a property of
the checkpoint record, which at 72 bytes per storage heal work admits about
58,000. The live Hoodi plan names millions of storage roots, so every
overflow-gated consumer was not made safe, it was permanently switched off:
promotedSubtrees was 0 in both live runs, SNAP-SYNC-FILL-STORAGE-THEN-HEAL's
zero-TrieNodes completion could never fire, and the pre-heal StorageRanges pass
was skipped whole.

Promotion is the load-bearing one. It is the only producer of shallow
whole-bucket :ACCOUNT subtree proofs, and a present depth-four :ACCOUNT proof is
the only thing that turns an account bucket from "descend" into a skip in
INTEGRATE-PRESENT-WORK. With promotion zeroed the only account proofs in
existence were the per-page ones from
SNAP-SYNC-CLASSIFY-ACCOUNT-RANGE-SUBTREES, which need a fully dirty subtree
inside one page's proved span: the preserved datadir-5c8a39c0 store holds 12,151
of them against a depth-four space of 65,536 buckets, beside 1,791,708 storage
subtree proofs. That asymmetry, not the 271,722 stale account markers, is what
made the account walk visit a million nodes. It is also the only one of the
account-side options that helps the post-rebase walk, where all twelve of the
observed live generations actually run: promotion runs from
SNAP-SYNC-PROMOTE-COMPLETE-RANGE-PLANS at heal entry over every plan root,
including the pre-rebase root whose plan is still durable.

No new trust is introduced. The invariant promotion already asserted is
unchanged: a trusted plan proves every account range and its code, and a bucket
containing a storage dependency that lacks both a completed task set and a
published whole-root closure is excluded. Only a width bound is removed. A
partial promotion is still never frozen as final, so incomplete buckets are
retried after their StorageRanges cursors finish.

Two properties of the streaming driver are load-bearing and were checked in
code rather than assumed:

1. No database iterator is open while a consumer body runs. Each segment's
   KV-ITERATOR is closed by SNAP-SYNC-DEFERRED-STORAGE-SEGMENT's
   UNWIND-PROTECT before the works are returned, and these consumers both read
   and write the same database. This follows the cursor-and-chunk style
   NODE-STORE-DATABASE-COPY-CHUNK already uses for the same reason.
2. The cursor walk cannot skip a plan entry, because nothing in the tree ever
   deletes one. SNAP-SYNC-POPULATE-DEFERRED-STORAGE-BATCH is the only writer of
   the snap-deferred-storage-v2: namespace and there is no corresponding delete;
   only the plan cursor is deleted, by SNAP-SYNC-DELETE-DEFERRED-STORAGE-CURSOR-
   BATCH.

The driver also fails closed on the one inconsistent read in this shape: a
segment that reports more work without a last identifier is a STORAGE-FAIL, not
a completion. Treating it as completion is how a plan silently loses its tail,
which is the 03263d2f and b23c7d57 signature. A zero or non-integer bound is a
caller error and signals before any read.

Batching the legacy retirement delete is conservative. The delete only removes
trust, so a crash before the batch applies leaves the pre-change state, which
the next heal entry retires again; and KV-APPLY-BATCH is a synchronous write
(rocksdb.lisp sets writeoptions_set_sync 1), so one apply per work would have
been millions of fsyncs at every heal entry once the width bound was gone.

Carried forward

Segmentation still does not apply after the first pivot rebase. The plan marker
is published only by SNAP-SYNC-COMMIT-ACCOUNT-PAGES when partial-root equals
state-root, and SNAP-SYNC-HEAL-REBASED-PROGRESS installs a sticky synthetic
witness, so a rebased root never gets a plan and the healer takes a state-root
walk for the rest of the session. Promotion is the part of this that does reach
those generations, because it runs over every durable plan root including the
pre-rebase one, but the frontier seeding does not.

The account-side closure problem itself is unsolved. Account marker absence
grants no skip and must not: an unmarked account subtree may still name code or
storage that is not durable. This change widens the supply of depth-four
:ACCOUNT proofs; it does not change what an account proof means. Options B
(stop writing account markers a page's own proof already covers, a frontier-size
win worth roughly 271,000 sentinel works and marker deletes per generation but
zero node visits) and C (advance the closure epoch to trust present unmarked
account nodes, high risk, blocked on the boundary-proof-node leg) remain open
and should be judged only after this change is measured live.

Still open from earlier revisions: the reproducible SBCL memory fault on
shutdown, and remote disk as the binding operational constraint.
