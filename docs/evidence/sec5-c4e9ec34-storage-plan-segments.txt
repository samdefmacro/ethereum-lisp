fix(snap): keep segmenting a storage plan across a heal checkpoint

This file is also 05c13ad55dd573ea075d0237b6478f4690ebcb0d's missing evidence.
That revision shipped two tests and no recorded RED control, which
docs/evidence/sec5-heal-stale-marker-trace.txt had explicitly demanded, because
segmentation changes when healing is considered complete -- the same semantics
that produced the 03263d2f and b23c7d57 false completions. Supplying the
control found that neither shipped test could fail, and that the resume path
published a false completion of exactly that class. Both are addressed here.

Change

05c13ad5 turned +snap-sync-deferred-storage-max-works+ into the parameter
*snap-sync-deferred-storage-max-works*, added SNAP-SYNC-DEFERRED-STORAGE-SEGMENT
and a durable snap-heal-storage-plan-cursor-v1: record, and made the healer
advance that cursor across consecutive segments instead of abandoning an
oversized plan for a state-root walk. The trace's measurement is why: one
storage heal work encodes to 72 bytes, so the four-megabyte checkpoint admits
about 58,000 while a live Hoodi plan names millions, and the fallback was
therefore always taken.

This revision changes two sites of that in src/networking/snap-sync/client.lisp
and nothing else in src/:

1. The heal entry (5680-5694) no longer discards the plan when a checkpoint is
   present. SNAP-SYNC-READ-DEFERRED-STORAGE-CURSOR is now called on every
   entry, so PLANNED-STORAGE-CURSOR and PLANNED-STORAGE-MORE-P describe the
   plan's real durable position on a resume.
2. The segment continuation (6916-6921) retires the heal checkpoint in the
   same batch as the cursor that closes the segment.

Why

A heal checkpoint records one segment's DFS frontier. It records nothing about
how far the plan itself has been closed -- only the cursor does that. As
05c13ad5 shipped, the entry returned (values nil nil nil nil) whenever a
checkpoint was present, so the cursor read sat in the discarded branch and was
never executed. When the checkpointed stack drained, the continuation guard
failed on its first conjunct, control reached the bare (return), and
SNAP-SYNC-COMPLETE-BATCH published completion while the same batch deleted the
cursor. Every segment past the cursor was abandoned and the record of where the
healer had stopped was destroyed.

This needs no crash to reach. PERSIST-CHECKPOINT (6094) fires from the local
path at 6904-6907 whenever CHECKPOINT-DUE-P holds with a bounded frontier, and
from the remote pipeline pause at 6694; +snap-sync-heal-checkpoint-node-interval+
is 128 x 2048 = 262,144 processed nodes. The live runs processed 0.85M and
14.97M nodes, so a checkpoint is written many times per generation, and
05c13ad5's continuation neither deleted nor refreshed it. Any operator stop,
OOM, the known SBCL shutdown fault, or a heal-yield the coordinator does not
follow with a rebase lands in it. Downstream the signature is b23c7d57's:
completed=true, an empty frontier, and a missing persisted trie node during
execution.

The fix is sound because the frontier cond at 5711-5721 already gives
CHECKPOINT-PRESENT-P priority, so PLANNED-STORAGE is computed and then ignored
on a resume; only the cursor and the more-p flag are taken from the plan. Three
consequences, each read in code rather than assumed:

1. Draining a checkpointed frontier completes the segment the checkpoint was
   taken inside, because the checkpoint is the whole frontier:
   RESTORE-BLOCKED-COMPLETIONS runs before PERSIST-CHECKPOINT on the pipeline
   path, DRAIN-DEFERRED-STORAGE runs before it on the local path, and
   CHECKPOINT-BLOCKS-TRAVERSAL-P keeps popped-but-unprocessed work out. So
   publishing that segment's cursor next is correct, and the final segment
   still yields more-p NIL and completes.
2. A checkpoint taken inside segment one leaves no cursor, and AFTER = NIL
   reloads segment one, whose own last identifier satisfies the guard.
3. The cursor can never become durable ahead of the content it certifies.
   FLUSH-HEALED-SUBTREES runs before the cursor batch, and per
   src/foundation/database/types.lisp 90-99 a later KV-APPLY-BATCH makes all
   preceding buffered writes durable before it returns. A crash before the
   cursor apply reheals already closed storage; a crash after it loads the
   next segment cleanly.

Retiring the checkpoint with the cursor is the smaller half. With the entry
fixed it is only tidiness -- a stale frontier would be re-walked cheaply --
but it keeps the two durable position records from ever disagreeing.

Carrying the cursor inside the checkpoint record instead would be strictly
larger: +snap-sync-heal-checkpoint-version+ is 4 at client.lisp 160, so it
needs a version bump and round-trip coverage, and it buys only the avoidance of
re-walking one already-closed segment.

Re-expressed, not weakened:
  snap-heal-storage-plan-segment-resumes-past-its-cursor now asserts its
    segment count -- five roots at a bound of two is exactly three segments.
    A loader that ignored AFTER used to make its unbounded loop hang the whole
    `sbcl --script` run with no result rather than report a failure.
  snap-heal-storage-plan-is-healed-in-consecutive-segments keeps its subject,
    but its comment no longer claims to prove segmentation. Measured: its plan

    and the segmentation code never runs. It remains a useful equivalence check
    that binding the parameter changes nothing on the ordinary import path.

Carried forward

1. Three SNAP-SYNC-DEFERRED-STORAGE-WORKS call sites still fail closed on an
   oversized plan and were deliberately left untouched here, because another
   agent owns them: SNAP-SYNC-PROMOTE-COMPLETE-RANGE-PLAN (client.lisp
   4994-5005), SNAP-SYNC-RANGE-PLAN-FULLY-DURABLE-P (4917-4922) and
   SNAP-SYNC-FILL-DEFERRED-STORAGE (5551-5559). The first is the account-side
   closure lever the live promotedSubtrees=0 identifies.
2. The two loaders disagree on their boundary. SNAP-SYNC-DEFERRED-STORAGE-WORKS
   flags overflow with `>` after pushing, i.e. at 8,193 works, while
   SNAP-SYNC-DEFERRED-STORAGE-SEGMENT caps with `>=` at exactly 8,192.
   Harmless today; not intended.
3. The deferred-storage plan marker is keyed by state root
   (SNAP-SYNC-DEFERRED-STORAGE-PLAN-IDENTIFIER, client.lisp 1941-1944, written
   for SNAP-SYNC-PROGRESS-STATE-ROOT at 2774). A pivot rebase therefore leaves
   the new root with no plan, SNAP-SYNC-DEFERRED-STORAGE-SEGMENT returns
   nothing, and the healer takes the state-root walk from then on. The
   5c8a39c0 run recorded twelve rebases; this one recorded none in its sampled
   window, so the interaction is read from code and unmeasured on a rebasing
   run.
4. The account side of closure is still unsolved, unchanged from
   docs/evidence/sec5-heal-stale-marker-trace.txt: an unmarked account subtree
   may still name code or storage that is not durable, and almost no account
   subtree can be skipped by proof either.
5. The reproducible SBCL memory fault on shutdown, seen on 0c6b51bf and
   646da589, remains unexplained.
6. Remote disk remains the binding operational constraint, and the live
   05c13ad5 datadir holds 53.71 GiB of it.
