Section 5 storage closure epoch

Revision

5c8a39c07489133248c7c2817c01288af4192485
fix(snap): trust closed storage subtrees during healing

Change

Closure epoch advanced from five to six. Epoch five is recognised but never
trusted, so an existing store keeps its content and its conservative walk. In a
store born under epoch six the healer now skips a present, unmarked, locally
read STORAGE node without descending, which is geth's AddSubTrie contract at
38271784c2b31926563806da9a2e023b88f5e7a8, trie/sync.go lines 289-297 and
630-640.

Why that is sound, and only for storage

Three properties, each verified in code rather than assumed:

1. Every persisted record is either marked incomplete or named in the range's
   complete references. SNAP-SYNC-INCOMPLETE-RECORD-HASHES takes the exact
   complement, and the account prebuffer at client.lisp 2426-2436 marks every
   record it writes without exception.
2. Complete references can only name subtrees rebuilt whole in the same batch.
   MPT-PROVED-RANGE-SUBTREES (foundation/trie/persistence.lisp 87-124) returns
   a node only when DIRTY-SUBTREE-P holds recursively for every descendant, and
   its docstring states that clean or unresolved proof-edge nodes are never
   returned.
3. A node cannot be separated from its marker. KV-APPLY-BATCH-BUFFERED is
   documented to "apply BATCH atomically without independently establishing a
   durable seam"; a crash drops whole trailing batches rather than splitting
   one.

Accounts are excluded deliberately. SNAP-SYNC-CLASSIFY-ACCOUNT-RANGE-SUBTREES
places a dependency-carrying account subtree into the same complete references,
so an unmarked account node may still own code or storage that is not durable.
That is the 03263d2f seam and it still requires the dependency proof.

    strict-inequality assertion fails.

  snap-healed-subtree-publication-waits-for-missing-descendants now mark their

    they modelled a store this epoch cannot produce.
  snap-complete-node-scheme-never-trusts-a-legacy-trie-store gains epoch five

Skipped subtrees now outnumber processed nodes more than six to one, where the
epoch-five run reached 25.6 million skips only after visiting 15.0 million
nodes. But the frontier still grows and there were 12 pivot rebases, so the
healer still cannot finish a generation inside a pivot window.

The remaining blocker is the account trie, and the numbers name it precisely:
knownIncompleteNodes (1,058,419) tracks processedNodes (1,058,816) almost
exactly. Every node the healer walks is marked, which means the account side is
entirely conservative and nothing there can be skipped. The account prebuffer
marks every record it writes, and the later page buffer only removes markers
for proved complete references; on this workload that removal evidently covers
very little. Why so few account markers are cleared is the next question, and
it is unanswered here.
