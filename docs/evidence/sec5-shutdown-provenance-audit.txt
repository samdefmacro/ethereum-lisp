1. `cffi:foreign-alloc`, `cffi:foreign-free`, `cffi:foreign-string-alloc` and

   foreign-alloc'd at all. Every foreign buffer is either a pinned Lisp vector
   (`cffi:with-pointer-to-vector-data`), a stack/`with-foreign-object`

   `*kzg-cffi-settings*` (cffi-verifier.lisp:49), `*secp256k1-context*`
   (secp256k1-ffi.lisp:95), and the RocksDB adapters cached in
   `*DEVNET-CLI-KV-DATABASE-CACHE*`. NONE of the three has a releaser that the
   serving node can reach. So the set of "early-startup foreign allocations
   freed at exit" that the brief asked to enumerate is EMPTY.

A3. PROVEN SAFE: the lazy global initialisers are not raced in the node.

    kzg-cffi-settings (cffi-verifier.lisp:52-62) and secp256k1-context

    In the node this cannot happen for KZG: call-with-devnet-cli-kzg-verifier

    secp256k1-context has no such forcing call and is reached lazily from

A4. PROVEN SAFE: no pinned-vector pointer can be taken on a non-simple vector.

    `cffi:with-pointer-to-vector-data` on SBCL is `sb-sys:vector-sap` under a
    pin. Handing it a displaced, adjustable or fill-pointered vector yields a
    pointer that is not the data, which would be an out-of-bounds foreign write
    -- an S2 mechanism. Every one of the 27 call sites is fed through
    `ensure-byte-vector` (bytes.lisp:14-24), `kzg-cffi-octets`
    (cffi-verifier.lisp:64-68), `bls12381-cffi-octets`
    (cffi-backend.lisp:48-52), `make-byte-vector` (bytes.lisp:6-9) or
    `kv-copy-bytes` (database/types.lisp:133-134).

    ensure-byte-vector is an `etypecase` whose first clause is the type
    `byte-vector` = `(simple-array (unsigned-byte 8) (*))` and whose other
    clauses build a fresh `make-array` with no fill pointer, no adjustability
    and no displacement. It therefore always returns a simple specialized
    vector, and a non-sequence input signals rather than producing garbage.
    This S2 class is eliminated.

A6. SUSPECTED, NOT PROVEN: the vendored io_uring retry.

    tools/rocksdb/io-uring-kernel-compat.patch is the only place this tree
    modifies third-party memory-management code. It inserts, into
    env/io_posix.h:341 (upstream CreateIOUring at :336-347):

        if (ret == -EINVAL) {
          ret = io_uring_queue_init(kIoUringDepth, new_io_uring, 0);
        }

    Re-initialising the SAME `struct io_uring` after a failure is the shape
    that would matter. Reasoning from liburing's documented contract:
    io_uring_queue_init_params leaves the ring untouched when the
    io_uring_setup syscall itself fails (the -EINVAL-on-unsupported-flags case
    the patch targets) and io_uring_queue_mmap memsets the ring to zero before

    freed twice. I therefore do NOT record a bad free here -- but this is
    reasoning from contract, not from the liburing source actually linked into
    the image, which I could not read in a reviewed container.

    What IS visible and is worth recording: DeleteIOUring (io_posix.h:331-334)

    performs a MultiRead leaks that ring's mmaps and its ring fd for the life
    of the process. That is upstream behaviour, not ours, but it is a leak that
    grows with thread churn and therefore with duration -- the same correlation
    the fault has.

What Part A means for S1 and S2

The addendum sets the test explicitly: "S1 ... CONFIRM: the offending free site
is identifiable by provenance alone, statically, without a long run." The audit
is complete over every site this tree owns and the site is not there. S1 is
therefore NOT confirmed, and the S1-in-our-code branch is closed.

S1 is not refuted, because a destructor-order defect entirely inside
librocksdb, libstdc++ or liburing remains possible, and A5 names the exact
destructor that would host one. S2 is not refuted either; A4 removes one
mechanism for it but a corrupting write inside third-party code is untouched by
a Lisp-side audit.

The single measurement that still discriminates them is unchanged and still
unrun: resolve pc to a library and symbol, per the addendum's "Why objdump did
not run, and what it needs". The audit narrows what that disassembly has to
explain: the freed chunk cannot be one of ours, so it is one of RocksDB's, and
A5 says which teardown is walking it.

What the fix has to be (Part A)

Unchanged from the original trace, and now better motivated. Closing the store
before exit removes the A5 teardown from a process that still has an open
database, which is the only exit-time free path this tree provokes. The
prerequisites in the original document stand: a closed-p guard on the backend
and a shutdown barrier, because the node today abandons threads that hold the
handle. Part B is the first instalment of that barrier.

===========================================================================
Part B. The graceful-stop time budget
===========================================================================

Why the 8551 Engine listener kept serving for ~50 s after 8545 closed

Three mechanisms compose, and none of them is a bug in isolation.

1. A shutdown request closes LISTENING sockets only.
   devnet-shutdown-request (src/app/cli/devnet/types.lisp:693-718) closes the
   engine and public listeners (:701-706) and then runs every registered
   closeable (:716-717). An accepted Engine HTTP connection is registered
   NOWHERE -- src/transport/http/server.lisp:175-211 accepts a connection and
   either hands it to a worker thread or serves it inline, and never registers
   it with the controller. So an established keep-alive connection is untouched
   by the stop.

2. The per-connection loop has no stop predicate.
   engine-rpc-http-service-handle-stream (server.lisp:3-62) loops until EOF or
   a `close-p` response. The `stop-p` predicate is consulted ONLY by the accept
   loop, at server.lisp:173-174. A consensus client that keeps using its pooled
   connection is therefore served indefinitely after the stop.

3. The listener's own unwind WAITS for that connection.
   server.lisp:214 calls engine-rpc-http-drain-connection-workers, whose budget
   is engine-rpc-http-worker-drain-timeout-seconds (server.lisp:86-90):

       5 + *engine-rpc-http-request-timeout-seconds*    (30, parser.lisp:18)
         + *engine-rpc-http-idle-timeout-seconds*       (120, parser.lisp:24)
       = 155 seconds.

This accounts for the recorded log exactly. The 8545 public listener reported
`listener.connections 0` and finished 66 ms after the shutdown request -- with
no connections there were no permits to reclaim, so its drain returned at once.
The 8551 Engine listener had three live Lighthouse connections; its workers
kept answering engine_newPayloadV4 and engine_forkchoiceUpdatedV3 from
10:07:58 to 10:08:41, and the three `streams`/`stream.finish` pairs inside
40 microseconds at 10:08:47.227 are those three workers being terminated at
once by SB-EXT:EXIT's %EXIT-OTHER-THREADS -- not by anything the application
did. The absence of any `listener.connections` / `listener.finish` line for
0.0.0.0:8551 in the log confirms that listener's unwind never completed.

Two properties matter more than any single number.

First, every bound is SEQUENTIAL and INDEPENDENT. The shutdown request that
wakes all of them is issued once, at the top, but each join then spends its own
fresh budget. The bounded steps alone sum to 91 s before peer sessions, and
devnet-join-peer-sessions is a per-thread `dolist` with 5 s + 5 s EACH
(peer-manager.lisp:1136-1142) -- with the nine peers the 3305307d run reported
at startup that term alone can reach 90 s.

Second, four joins have no bound at all, and the database export has none.

So the observed 52 s was a fast case, not a typical one, and no configuration
of this code can promise 30 s. That is why 05c13ad5 was SIGKILLed at exit 137.

The fix that landed

Four parts, all inside src/transport/http/, all of them go-ethereum's
http.Server.Shutdown semantics rather than an invention of ours: stop
accepting, stop reusing established connections, let what is in flight finish
under a deadline, then close whatever the deadline did not reclaim.

1. The per-connection loop honours the listener's stop predicate.
   engine-rpc-http-service-handle-stream takes `:stop-p` and returns BETWEEN
   requests once a stop has been requested; engine-rpc-http-serve-connection
   and both dispatch sites in serve-listener thread it through. The check sits
   at exactly one place in that loop, so a request already in flight is
   answered in full -- dropping a response mid-write would make a graceful stop
   worse than a SIGKILL -- and only the wait for the NEXT request is cut short.

2. The wait between requests polls instead of parking.
   A stop predicate is useless to a worker blocked in one 120-second read, and
   a pooled connection spends nearly all of its life exactly there. The new
   engine-rpc-http-await-next-request splits that wait into
   *engine-rpc-http-stop-check-interval-seconds* (new, default 1) slices under
   SB-SYS:WITH-DEADLINE, rechecking the stop between them. The idle budget is
   NOT changed: the slices are measured against the same
   *engine-rpc-http-idle-timeout-seconds* deadline and it still expires at the
   same moment and with the same error. This is what covers the idle case that
   the original draft of this document listed as unfixed; the round trip
   through the devnet shutdown controller a connection closeable would have
   needed is not required, and the transport keeps its independence from the
   CLI layer.

3. The drain budget collapses once a stop has been requested.
   engine-rpc-http-worker-drain-timeout-seconds takes an optional STOPPING-P
   and then returns *engine-rpc-http-shutdown-drain-seconds* (new, default 5)
   instead of 5 + 30 + 120. With (1) and (2) in place the only thing left to
   wait for is a single request already in progress, so the idle timeout no
   longer belongs in the budget.

4. The listener closes what the drain abandoned.
   serve-listener now keeps a lock-guarded registry of accepted connections and
   closes whatever is still in it after the drain gives up, logging
   engine.rpc.http.listener.abandoned with the count when that happens. Closing
   a LISTENING socket never touched an established one, so before this the only
   thing that ever released such a connection was the process exiting -- which
   under a grace period means SIGKILL. A connection that finishes normally is
   deregistered by the same unwind that releases its worker permit, so the
   registry is empty on every ordinary stop and nothing is closed twice.

Bound on the HTTP contribution of a stop: one
*engine-rpc-http-stop-check-interval-seconds* for an idle connection to notice,
plus at most *engine-rpc-http-shutdown-drain-seconds* per listener for a
request in flight, plus the 11 s of engine accept-thread joins. Measured 0.81 s
busy and 1.01 s idle end to end. It does NOT bound the whole stop; see below.

Every HTTP surface that shares this code was checked, not just the one the
regression drove:

  public JSON-RPC (8545)  same serve-listener, same service struct. Covered.
  Engine API (8551)       same, plus JWT. The stop check is in the connection
                          loop, above authentication, so a peer that cannot
                          authenticate cannot hold a stop either. Covered.
  WebSocket / eth_subscribe
                          does NOT share this code. It already had a `:stop-p`
                          on its pump with a one-second poll gate, and every
                          accepted socket is already a registered closeable
                          (ws-server.lisp:282-286). Verified rather than
                          changed: the new test
                          WEBSOCKET-SUBSCRIBER-DOES-NOT-HOLD-A-SHUTDOWN leaves
                          a subscribed socket OPEN across the shutdown request
                          and joins the session thread, which the pre-existing
                          end-to-end test could not show because it closes its
                          socket first.
  metrics                 does NOT share this code either. Its reads are
                          bounded by +devnet-metrics-read-timeout-seconds+ and
                          its accept is readiness-gated, so a silent scraper
                          cannot hold it. No hazard found, nothing changed.

What it does not fix, and the plan for the rest

The join summation needs one shared deadline, not fifteen independent ones.
The shape: put a deadline on the shutdown controller, set on the first
devnet-shutdown-request; derive every join timeout in service.lisp:238-336 and
in devnet-join-peer-sessions from the REMAINING budget rather than from a fixed
5 or 15 s. The total then becomes the budget plus one terminate, instead of the
sum of every step. This was deliberately NOT bundled here: bounding the four
currently-unbounded joins changes which threads can be abandoned, and the
per-thread peer-session loop needs a budget shared across all sessions rather
than per session. Both are behaviour changes that deserve their own review and
their own tests, and the regression test added here is the harness they extend.

RED and GREEN

Six tests, in three layers. The two e2e ones launch a real node process, open
one HTTP connection to the public RPC endpoint, send SIGTERM via the pid file,
and measure the wall-clock time to process exit against a 20 s budget. That
budget is the point of them: a supervisor stops the node with a fixed grace
period -- the Hoodi gate uses `docker stop --time 30` -- and a stop that
outlasts it loses the unwind, the database export and the exit status.

e2e, tests/cli-runner-edge-tests.lisp:

  DEVNET-CLI-SIGTERM-STOPS-A-NODE-SERVING-A-KEEP-ALIVE-CONNECTION
    A driver thread keeps issuing keep-alive eth_chainId requests on the pooled
    connection straight through the shutdown. CONFIRMED RED on the unmodified
    tree twice, on 2026-09-18 and again on 2026-09-19 before this change: the
    process did not exit within the 20 s budget. GREEN after, at 0.81 s.

  DEVNET-CLI-SIGTERM-STOPS-A-NODE-HOLDING-AN-IDLE-KEEP-ALIVE-CONNECTION
    New. The half a busy client cannot reach: the connection is opened, proved
    reusable, then left silent so the worker serving it is parked in the wait
    for the next request when the signal arrives. It reuses the connection once
    more AFTER a silent interval, so a stop cannot look fast merely because the
    server had already closed a connection the test believes it holds. GREEN at
    1.01 s.

integration, tests/websocket-tests.lisp and tests/core-http-service-tests.lisp:

  WEBSOCKET-SUBSCRIBER-DOES-NOT-HOLD-A-SHUTDOWN
    New. An open eth_subscribe session across the shutdown request, with the
    live session thread asserted alive first so the measurement cannot be of a
    connection that had already ended.

  ENGINE-RPC-HTTP-LISTENER-CLOSES-A-CONNECTION-THE-DRAIN-ABANDONED
    New. A worker held inside its read past the drain budget; the assertion is
    that the LISTENER closed that connection, before the worker's own unwind
    could.

unit, tests/core-http-service-tests.lisp:

  ENGINE-RPC-HTTP-STOP-ANSWERS-THE-REQUEST-IN-FLIGHT-AND-STARTS-NO-MORE
    New, and it pins both edges from one stream carrying two requests: with a
    stop, exactly one 200 is written and its body is complete; with no stop,
    the control leg answers both. A stop consulted too early fails the first
    assertion, a stop never consulted fails the second, and the control proves
    the fixture was answerable either way.

  ENGINE-RPC-HTTP-IDLE-WAIT-RETURNS-ONCE-A-STOP-IS-REQUESTED
    New. The stop arrives while the connection is blocked in a read that would
    otherwise take 20 s. Its positive control is the same blocked read with no
    stop at all, which must still expire on the idle deadline -- so the poll
    cannot have turned the wait into an early return.

  ENGINE-RPC-HTTP-WORKER-DRAIN-COLLAPSES-ONCE-A-STOP-IS-REQUESTED
    New. 155 s without a stop, the parameter's value with one, and a second
    binding proves it is the parameter rather than a constant that happens to
    match the other branch's floor.
    ENGINE-RPC-HTTP-WORKER-DRAIN-OUTLASTS-BOTH-DEADLINES is left untouched as
    the no-stop control.

Carried forward

- The pc-to-symbol resolution remains unrun and remains the one measurement
  that separates S1 from S2. Part A narrows what it must explain: the chunk is
  not one this tree allocated or frees.
- Closing the store on the node shutdown path is still the right change, and
  A5 names the teardown it removes.
- NEW, and it belongs to whoever owns the exit-time memory fault: this fix
  makes that fault MORE reachable, not less. Until now a live `docker stop
  --time 30` SIGKILLed the node while it was still serving, so the process
  never reached exit(3) and never ran the A5 teardown at all. A stop that now
  completes in about a second runs the whole unwind and then exit(3) with the
  RocksDB thread pools still populated, which is exactly the path A5 describes.
  Expect the fault's observed frequency on the Hoodi gate to go UP; that is the
  fix working, not a regression it introduced.
- The WebSocket accept loop registers every accepted socket as a shutdown
  closeable and never removes it (ws-server.lisp:282-286), so the closeable
  list grows for the life of the node with one entry per WebSocket connection
  ever accepted. Each is an IGNORE-ERRORS close of an already-closed socket at
  shutdown, so it is a slow leak and not a correctness fault. Not touched here;
  the matching remove-closeable call is the fix.
- The cleanup joins still sum rather than share a deadline; four of them and
  the database export are still unbounded.
- secp256k1-context (secp256k1-ffi.lisp:97-108) is still an unsynchronised lazy
  initialiser reached from many threads. It leaks at most one context and
  cannot double-free, so it is a tidiness item, not a shutdown item.
- E4 from the original trace is untouched: the SIGTERM handler still takes a
  mutex and runs closeable thunks in the signal context (types.lisp:745-748).
